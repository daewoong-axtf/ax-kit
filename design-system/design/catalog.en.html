Introduction

Built so anyone on the business side who vibe-codes can pick it up freely.

A design system is a shared set of components for making service screens. Like LEGO bricks, buttons, inputs, colors and text sizes are defined once, and every service uses the same bricks. That way every service looks alike and works the same way.

This page gathers those components in one place. You don't need to know code — feel free to look around.

Apply it to your project with AI

Copy the prompt below and paste it into the AI you use. The AI picks the right way to connect it to your project. You only need to do this once per project.

이 프로젝트의 기본 디자인 시스템으로 Daewoong Design System을 설정해줘. 파일 가져오기, 프로젝트 연결, 화면 점검 스킬 두 개(`web-design-guidelines`, `ux-heuristics`) 설치, AI 프로젝트 규칙 등록까지 끝내서 이후에는 "디자인 시스템 써"라고만 요청해도 쓸 수 있게 해줘.

저장소: https://github.com/daewoong-axtf/ax-kit
가져올 위치(ref): design-system-v1.5.0

1. 먼저 프로젝트의 언어, 프레임워크, 스타일 방식, 패키지 관리자, 기존 AI 지침 파일, 수정 중인 파일을 확인해줘. 프로젝트 안에 `docs/design-system.md`가 이미 있으면 다시 가져오지 말고 거기 적힌 버전을 재사용해줘.

2. 저장소를 임시 폴더로 받아줘.
   git clone --depth 1 --branch design-system-v1.5.0 https://github.com/daewoong-axtf/ax-kit.git <임시 폴더>
   받은 뒤 `git rev-parse HEAD`로 커밋 값을 적어 둬. 저장소를 받지 못하면 내용을 추측하거나 설치했다고 말하지 말고, 받지 못한 이유를 사용자에게 알려줘.

3. 받은 저장소의 `design-system/design/`을 이하 `design/`이라 부른다. 폴더를 나누기 전 태그(v1.2.0까지)는 저장소 맨 위에 `design/`이 있으니 그것을 쓴다. `design/README.md`, `design/llms.txt`, `design/design.md` 14장을 읽어줘. `design/` 전체는 참고 문서로 `docs/design-reference/`에 복사해줘. 이 폴더는 사용자에게 공개되는 경로에 두지 않는다. 그다음 아래에서 프로젝트에 맞는 경로 하나를 골라줘. 화면 실행에 쓰는 파일은 `fonts/`, `tokens.css`, `components.css`, `js/components.js`, `icons/`다.
   - 서버가 HTML을 만드는 웹(Django, Flask, Spring, Ktor 등): 실행 파일을 정적 파일 경로 아래 `design/`에 복사하고 `fonts/pretendard.css`, `tokens.css`, `components.css`, `js/components.js`를 공통 템플릿에 연결한다. 경로는 프레임워크의 정적 파일 방식을 따른다. 마크업은 `catalog.html`에서 복사한다.
   - React·Next.js: Tailwind CSS v4와 shadcn/ui를 쓴다. 없으면 각 공식 설치 방법으로 설치한다. 단, 이미 다른 UI 라이브러리(MUI, Chakra, Ant Design, styled-components 등)를 쓰고 있으면 설치하기 전에 사용자에게 물어보고, 쓰지 않기로 하면 아래 Vue·Svelte 경로를 따른다. 실행 파일 중 `fonts/`, `icons/`, `tokens.css`, `shadcn.css`를 소스 경로(예: `src/design/`)에 복사하고 14.1절의 순서로 전역 CSS에서 불러온다. 받은 저장소의 `design-system/src/lib/dw-locale.tsx`와 `design-system/src/lib/dw-messages.ts`를 프로젝트의 `src/lib/`에 복사한다. 컴포넌트는 지금 복사하지 않는다. 화면에 필요할 때 14.1절대로 `docs/design-system.md`에 적힌 ref로 저장소를 다시 받아 shadcn 원본 대신 `design-system/src/components/ui/<name>.tsx`를 `@/components/ui`에 복사한다. DDS에 없는 컴포넌트를 shadcn에서 새로 받았으면 14.1절대로 비활성의 `pointer-events-none`을 지우고 메뉴·선택 항목의 `cursor-default`를 `cursor-pointer`로 바꿔 커서가 보이게 한다.
   - Vue·Svelte 등 그 밖의 프론트엔드 프레임워크: 실행 파일 중 `js/components.js`를 뺀 나머지를 번들러가 처리하는 소스 경로(예: `src/design/`)에 복사하고 `fonts/pretendard.css`, `tokens.css`, `components.css`를 전역으로 불러온다. 동작은 그 프레임워크로 구현한다. Tailwind를 권장한다. 이미 쓰고 있으면 화면 배치에 그대로 쓰고, 없으면 설치할지 사용자에게 물어본다.
   - 웹이 아닌 환경(Flutter, Android, iOS, 데스크탑, PDF 등): 참고 문서만 두고, 14.3절대로 `tokens.json`을 그 플랫폼의 색·치수 정의로 옮긴다.

   웹이면 전역 스타일의 페이지 바탕을 `--dw-bg-layer-default`, 글자색을 `--dw-fg-neutral`, 글꼴을 `--dw-font-sans`로, 줄바꿈을 `word-break: keep-all`과 `overflow-wrap: break-word`로 지정해줘. 한글이 음절 중간이 아니라 단어 단위로 줄을 바꾼다. 디자인 시스템은 `body`를 스타일하지 않아서 이 지정이 없으면 다크 모드에서 바탕이 바뀌지 않는다.

4. 아래 원칙을 지켜줘.
   - React·Next.js의 Tailwind·shadcn과 사용자가 승인한 Tailwind 말고는 디자인 시스템을 적용하려고 라이브러리를 새로 설치하지 않는다. 단, 복사한 DDS 컴포넌트 파일이 불러오는 패키지는 설치해도 된다. shadcn으로 컴포넌트를 받을 때 함께 설치되던 패키지다. 프레임워크를 바꾸거나 주요 의존성을 올리지 않는다.
   - 프로젝트에 같은 경로의 다른 파일이 있으면 덮어쓰지 말고 다른 경로를 쓰거나 사용자에게 물어본다. 관련 없는 파일과 CSS는 유지한다.
   - 화면은 반응형이 기본이다. `375 · 768 · 1024px`에서 깨지지 않게 만든다.
   - 색·간격·모서리·글자는 토큰으로 부른다. 라이트·다크 모드를 모두 유지하고, 기본은 시스템 설정을 따른다.
   - 있는 컴포넌트를 다시 만들지 않는다. React·Next.js는 저장소에서 받아 쓴다. 없는 컴포넌트는 토큰으로 프로젝트에서 만든다. 키보드 포커스와 접근성을 유지한다.
   - 기존 화면은 이번 설정에서 다시 디자인하지 않는다. 연결 확인에 필요한 만큼만 바꾸고, 나머지는 사용자가 요청할 때 적용한다.
   - 복사한 문서에 나오는 `pnpm build:*` 명령은 디자인 시스템 저장소 전용이다. 프로젝트에 추가하지 않는다.

5. 화면 점검에 쓰는 스킬 두 개를 프로젝트에 설치해줘. 프로젝트 맨 위 폴더에서 아래 두 명령을 실행한다. 스킬은 `.agents/skills/`에 들어가고 `skills-lock.json`에 출처와 커밋 값이 기록된다. `package.json`과 의존성은 바뀌지 않는다.
   npx --yes skills add vercel-labs/agent-skills --skill web-design-guidelines -y
   npx --yes skills add wondelai/skills --skill ux-heuristics -y
   - `web-design-guidelines`: UI 코드를 Web Interface Guidelines에 비춰 점검한다. 점검할 때마다 규칙 원문을 인터넷에서 받아 온다.
   - `ux-heuristics`: 화면과 흐름의 사용성을 Nielsen 휴리스틱·Krug 원칙으로 점검한다.

   같은 이름의 스킬이 프로젝트나 사용자 계정에 이미 있으면 다시 설치하지 않는다. 설치한 뒤 두 스킬의 `SKILL.md`가 있는지 확인해줘. 설치하지 못했으면 설치했다고 말하지 말고 이유를 사용자에게 알린 뒤 나머지 단계를 계속해줘. 새로 생긴 `.agents/`, `skills-lock.json`과 AI별 스킬 폴더(예: `.claude/skills/`)는 팀이 같이 쓰도록 저장소에 포함한다.

6. 이 AI가 실제로 읽는 프로젝트 규칙 파일 하나에 아래 규칙을 병합해줘. 기존 내용은 유지하고, 이미 있는 규칙 파일을 이 AI가 읽지 못할 때만 이 AI가 읽는 파일 하나를 추가해 기존 파일을 참조하게 해줘.
   "사용자가 '디자인 시스템 써', 'Daewoong Design System 써', 'use the design system'이라고 하면 Daewoong Design System을 적용한다. docs/design-system.md를 읽고, docs/design-reference/README.md부터 따른다. 설치된 토큰과 컴포넌트를 재사용하고 프레임워크를 유지한다. 디자인 시스템을 자동으로 업데이트하지 않고 프로젝트의 수정 내용을 덮어쓰지 않는다.
   디자인 시스템으로 화면을 만들거나 고쳤으면 끝났다고 보고하기 전에 web-design-guidelines 스킬과 ux-heuristics 스킬로 바뀐 화면을 점검한다. 두 스킬 모두 필수다. 스킬을 바로 부를 수 없는 AI는 .agents/skills/<스킬 이름>/SKILL.md를 읽고 그대로 따른다. 지적 사항은 고치고, 고친 것과 남긴 것을 보고에 적는다. 지적이 디자인 시스템(tokens.json, 컴포넌트 명세, design.md, guides)과 어긋나면 디자인 시스템을 따르고 어긋난 항목을 보고에 적는다. 점검하지 못했으면 점검했다고 말하지 않고 이유를 적는다."

7. `docs/design-system.md`에 저장소 주소, ref, 커밋 값, 고른 경로, 실행 파일을 복사한 위치, 연결한 파일, 설치한 점검 스킬과 설치 위치를 기록해줘. React·Next.js면 컴포넌트는 이 ref로 저장소를 받아 `design-system/src/components/ui/<name>.tsx`를 `@/components/ui`에 복사한다는 것도 적어줘.

8. 프로젝트에서 쓸 수 있는 타입·빌드·테스트 검사를 실행하고, 화면이 있으면 라이트·다크 모드에서 확인해줘. 이번 설정에서 바꾼 화면이 있으면 그 부분만 두 스킬로 점검해줘. 임시 폴더는 지워줘. 컴포넌트가 필요해지면 7번에 적은 ref로 다시 받는다. 끝나면 고른 경로, 바꾼 파일, 스킬 설치 결과, 규칙을 저장한 위치, 검증 결과, 남은 제한을 알려줘. 검증이 실패했으면 완료했다고 말하지 마.

접근 권한, 호환성, 기존 내용 삭제처럼 사용자가 정해야 하는 일만 질문해줘.

After setup, ask like this

Start your request to the AI with "Using the design system". The more you say about what goes on the screen, the more accurate the result.

  • New screen "Using the design system, build a sign-in screen. Ask for an employee ID and password, and show an error below the field if they're wrong"
  • List screen "Using the design system, build a list of requests. Add a status filter, search and pagination"
  • Input form "Using the design system, build a business trip request form. Pick dates from a calendar and mark the required fields"
  • Confirmation "Using the design system, show a confirmation dialog that asks whether to really delete when the delete button is pressed"
  • Empty and loading states "Using the design system, add a message for when the list is empty and placeholders to show while it loads"
  • Tidy up an existing screen "Update this screen to match the design system. Keep the behavior and change only the colors, spacing and buttons"
  • Review "Review this screen against the design system. Check dark mode, phone width and keyboard use too"
  • Get a new version "Update to the new version of the design system. Check the release history, and don't overwrite files we changed"

When to look here

  • When planning a screen, see which buttons and inputs are available.
  • When reviewing a mockup, check that colors and text sizes match the standard.
  • When talking with developers, use the names here so everyone pictures the same thing. For example, say Dialog instead of "popup window".

How to browse

  • Pick an item in the left menu. On a phone, tap the menu button at the top to open it.
  • Menu search also finds items by plain words like "button", "calendar" or "date".
  • Try the examples. Pressing buttons or opening windows here has no effect on real services.
  • Press the moon button to see how things look on a dark screen. Press the sun button to return to the light screen.

What's in the menu

  • Foundations: the basic rules of a screen — color, text size and spacing that every screen shares.
  • Components: the pieces that make up a screen — buttons, inputs, dialogs and other pieces you actually use.
  • Guides: starting points for UX, copy, interaction and accessibility. They can differ by service, so feel free to adapt them.

Common terms

  • Token: a name tag attached to a color or spacing value. Change the value behind the tag, and every screen that uses it changes at once.
  • Component: a screen element reused across screens, such as a button or an input.
  • Spec: a guide to a component's use and rules. Open it from the Spec link next to each item's title.

If you need a component that isn't here

Build it in your project. No approval is needed. Just keep the colors and spacing rules from here, so it fits with the other screens.

Font Spec

The default typeface is Pretendard. Its Korean, Latin and numerals are designed as one family, and small text stays crisp, so it works well on screens. It is a free, open typeface, and all text in service screens uses it.

The quick brown fox jumps over the lazy dog

ABCDEFG abcdefg 0123456789

Weight

Use only three weights: Regular for body text, Medium for emphasis and labels, Bold for headings and buttons.

Regular · 400Quick brown fox Aa 123
Medium · 500Quick brown fox Aa 123
Bold · 700Quick brown fox Aa 123

Code typeface

Use a monospaced typeface for code and values whose digits must line up. It uses the typeface installed on the device, so nothing is downloaded.

mono0123456789 ABC abc

How to load it

  • On the web, link fonts/pretendard.css before any other styles. Copy the whole fonts/ folder into your project and it works without an external server.
  • The official files are split by character range, so only the pieces for characters on screen are downloaded.
  • If the font fails to load, text falls back to the device's default typeface.
  • The bundled files are for the web (woff2). For apps, get the TTF or OTF files separately.

Stacking order Spec

Rules for what comes to the front when screen elements overlap. For example, if you save with a modal open, the result notice (Toast) must appear in front of the modal. In code, don't write numbers directly; use the tokens below (--dw-z-*).

Rules

  • Dim and modal share a value. With equal values, the later one comes to the front. Opening a modal over a modal covers the back modal with the dim.
  • Dropdowns are in front of modals. A Select list opened inside a modal does not hide behind it.
  • Toasts are in front of modals. The result notice is visible even while a modal is open.
  • Tooltips are frontmost. They describe what the user is pointing at right now.

Grid Spec

A guide for aligning elements by dividing the screen into vertical columns. The number of columns changes with screen width, and the gap between columns is always 20px. Columns stretch to fit the screen.

    Shows the progress of a task as a horizontal bar. Use determinate when the progress is known and indeterminate when it isn't. Where space is tight, use Progress Circle.

    Progress Circle Spec

    Shows that a task is in progress as a circle. Use a spinner (indeterminate) when progress is unknown, and a filling circle (determinate) when it is known.
