이 프로젝트에 설치된 Daewoong Design System(DDS)을 새 판으로 올려줘. 프로젝트에서 고치지 않은 파일은 묻지 말고 새 판으로 바꾸고, 프로젝트에서 고친 파일을 새 판도 바꿨을 때만 어떻게 할지 한 번에 물어줘.

저장소: https://github.com/daewoong-axtf/ax-kit.git
최신 판: https://daewoong-axtf.github.io/ax-kit/guides/index.json 의 `guides["design-system"].latest`

이 글에서 쓰는 이름은 아래와 같다.
- **기록**: 프로젝트의 `docs/design-system.md`. 설정할 때 남긴 저장소 주소, ref, 커밋 값, 고른 경로, 실행 파일을 복사한 위치, 연결한 파일이 적혀 있다.
- **지금 판**: 기록에 적힌 ref. **올릴 판**: 2번에서 정하는 ref.
- **태그 이름**: 1.2.0까지는 `v<판>`(`v1.0.0`~`v1.2.0`), 그 뒤로는 `design-system-v<판>`(`design-system-v1.3.0`부터)이다.
- **`<OLD>` · `<NEW>`**: 지금 판과 올릴 판을 받은 임시 폴더 안의 디자인 시스템 폴더. 받은 폴더에 `design-system/design/`이 있으면 `<임시 폴더>/design-system/`이고, 없으면 `<임시 폴더>/` 자신이다. 폴더를 나누기 전 태그 `v1.0.0`~`v1.2.0`은 저장소 맨 위에 `design/`·`src/`·`package.json`이 있고, `design-system-v*` 태그는 `design-system/` 아래에 있다. 이하 `<OLD>/design/`, `<NEW>/src/components/ui/`처럼 쓴다.
- **실행 폴더**: 기록에 적힌, 실행 파일(`fonts/`, `icons/`, `tokens.css` 등)을 복사한 프로젝트 안의 폴더 (예: `src/design/`, `static/design/`).

묻는 것은 9번의 한 번이 원칙이다. 그 밖에는 1번(고른 경로나 실행 폴더를 정할 수 없을 때), 2번(올릴 판이 지금 판보다 낮을 때), 9번의 합치기 충돌, 진행을 막는 접근 권한·호환성 문제(예: 패키지를 설치할 수 없다)에서만 묻는다.

어느 단계에서 멈추든 이번에 받은 임시 폴더(OLD·NEW, 받다가 실패한 폴더 포함)는 지우고 멈춘다.

1. 기록을 읽어줘.
   - `docs/design-system.md`가 없으면 이것은 업그레이드가 아니라 처음 설정이다. 사용자에게 그렇게 알리고 여기서 멈춘다. 처음 설정은 설정 프롬프트(`https://daewoong-axtf.github.io/ax-kit/guides/design-system/latest.md`)로 한다.
   - 기록에서 저장소 주소, ref, 커밋 값, 고른 경로(서버 템플릿 웹 · React·Next.js · 그 밖의 프론트엔드 · 웹이 아닌 환경), 실행 폴더, 연결한 파일, 복사한 파일 목록(있으면)을 확인한다. 실행 폴더가 적혀 있지 않으면 프로젝트에서 `tokens.css`를 찾아 정한다. 웹이 아닌 환경은 실행 폴더가 없다. 고른 경로나 웹의 실행 폴더를 정할 수 없으면 사용자에게 묻는다. 기록에 ref가 없으면 묻지 않는다. 2번의 버전 비교를 건너뛰고 3번에서 OLD 없이 계속한다.
   - 프로젝트의 AI 규칙 파일(`AGENTS.md`, `CLAUDE.md`, `.cursor/rules/` 등)에서 디자인 시스템을 적은 곳도 찾아 둔다. 9번에서 고친다.
   - git 저장소면 `git status --porcelain`으로 커밋하지 않은 변경(추적하지 않는 파일 포함)을 적어 둔다. 디자인 시스템 파일의 커밋하지 않은 변경도 프로젝트에서 고친 내용으로 본다. 9번에서 쓴다.

2. 올릴 판을 정해줘.
   - 사용자가 판을 말했으면 그 판이다. 버전만 말했으면(`1.6.0`, `v1.6.0`) 위 태그 이름 규칙으로 태그를 만든다. `1.6.0`은 `design-system-v1.6.0`, `1.2.0`은 `v1.2.0`이다. 태그 이름을 그대로 말했으면 그대로 쓴다. `main` 같은 브랜치를 말했으면 그 브랜치를 올릴 판으로 쓰고, 아래 버전 비교는 건너뛴다.
   - 말하지 않았으면 최신 릴리즈다. `curl -fsSL https://daewoong-axtf.github.io/ax-kit/guides/index.json`의 `guides["design-system"].latest`가 `1.6.0`이면 태그는 `design-system-v1.6.0`이다. 받지 못하면 `git ls-remote --tags https://github.com/daewoong-axtf/ax-kit.git "design-system-v*"`에서 가장 높은 판을 쓴다. 둘 다 안 되면 이유를 알리고 멈춘다.
   - 지금 판의 버전은 ref에서 읽는다. `v1.2.0`은 1.2.0, `design-system-v1.4.0`은 1.4.0이다. 올릴 판과 같으면 이미 그 판이라고 알리고 멈춘다. 저장소는 받지 않는다. 올릴 판이 더 낮으면 내리는 것이므로 멈추고 사용자에게 묻는다. 기록에 ref가 없거나, 지금 판이나 올릴 판이 태그가 아니면(`main` 같은 브랜치, 커밋 값) 이 비교는 건너뛴다.

3. 두 판을 임시 폴더로 받아줘. 프로젝트 안에 받지 않는다. 임시 폴더는 `mktemp -d`로 만든다.
   NEW=$(mktemp -d) && git clone --depth 1 --branch <올릴 판> https://github.com/daewoong-axtf/ax-kit.git "$NEW"
   OLD=$(mktemp -d) && git clone --depth 1 --branch <지금 판> https://github.com/daewoong-axtf/ax-kit.git "$OLD"
   - 기록의 저장소 주소가 `daewoong-design-system`이나 `daewoong-ax-standards`로 끝나도 예전 이름일 뿐이다. 언제나 위 `ax-kit` 주소로 받는다. 옛 태그 `v1.0.0`~`v1.2.0`도 이 주소에 있다.
   - `dds` 스킬이 올릴 판을 이미 받아 두었으면 그 폴더를 NEW로 쓰고 다시 받지 않는다.
   - NEW에서 `git rev-parse HEAD`로 커밋 값을 적어 둔다. NEW를 받지 못하면 내용을 추측하지 말고 이유를 알리고 멈춘다.
   - 아래 경우에는 OLD를 쓰지 않고 OLD 없이 계속한다: 기록에 ref가 없다(이때는 OLD를 받지 않는다), 지금 판이 태그가 아니다(`main` 같은 브랜치, 커밋 값), OLD를 받지 못했다, 기록에 커밋 값이 없다, OLD에서 `git rev-parse HEAD`로 읽은 커밋 값이 기록의 커밋 값과 다르다. 그 이유를 적어 두었다가 9번 질문 맨 위에 쓴다. OLD 없이 계속하면 5번에서 NEW와 같은 파일만 묻지 않고, 나머지는 모두 "고친 파일"로 본다.
   - 위 정의대로 `<OLD>`와 `<NEW>`를 정한다. 두 판의 폴더 구조가 달라도 비교는 `<OLD>/design/tokens.css`와 `<NEW>/design/tokens.css`처럼 같은 상대 경로끼리 한다.

4~8번은 무엇을 할지 정하고 목록으로 적어 두기만 한다. 프로젝트 파일을 쓰거나 지우는 일, 새 파일을 넣는 일, 패키지를 설치하는 일은 모두 9번에서 질문에 답을 받은 뒤 한다.

4. 비교할 파일을 모아줘. 프로젝트 파일 하나마다 짝이 되는 `<OLD>` 파일과 `<NEW>` 파일을 정한다.
   - 실행 폴더: 실행 파일은 `fonts/` · `icons/` · `tokens.css`와, 고른 경로에 따라 `shadcn.css`(React·Next.js), `components.css`(서버 템플릿 웹, 그 밖의 프론트엔드), `js/components.js`(서버 템플릿 웹)다. `<NEW>/design/ai/setup-prompt.md`의 경로별 안내와 같다. 실행 폴더 안의 파일은 실행 폴더 기준 상대 경로가 같은 `<OLD>/design/`·`<NEW>/design/`의 파일과 짝이다. 예: `src/design/tokens.css` ↔ `design/tokens.css`, `src/design/fonts/pretendard.css` ↔ `design/fonts/pretendard.css`. 고른 경로의 실행 파일 중 `<NEW>/design/`에만 있는 파일(새 아이콘, 새 글꼴 조각)도 목록에 넣는다. 실행 폴더 안의 파일 중 `<OLD>/design/`에도 `<NEW>/design/`에도 없는 파일은 프로젝트의 것이다. 목록에 넣지 않고, 건드리지 않고, 묻지 않는다.
   - React·Next.js 컴포넌트: 프로젝트의 `ui` 폴더는 `components.json`의 `aliases.ui`이고, 없으면 `@/components/ui`다. 별칭은 `tsconfig.json`의 `paths`로 실제 폴더(보통 `src/components/ui/`)를 찾는다. 그 폴더의 `<name>.tsx` 중 `<OLD>/src/components/ui/` 또는 `<NEW>/src/components/ui/`에 같은 이름이 있는 파일이 대상이다. 짝은 `<OLD>/src/components/ui/<name>.tsx`와 `<NEW>/src/components/ui/<name>.tsx`다. DDS에 같은 이름이 없는 파일은 프로젝트의 것이므로 건드리지 않는다. DDS에만 있고 프로젝트에 없는 컴포넌트는 새로 넣지 않는다(7번의 의존 파일만 예외).
   - shadcn에서 받은 컴포넌트: 1.5.0보다 낮은 판의 설정 프롬프트는 컴포넌트를 DDS 저장소가 아니라 `npx shadcn add`로 받게 했다. 컴포넌트를 DDS에서 복사했다고 보는 것은 기록이 아래 둘 중 하나를 담을 때뿐이다.
     - 기록의 "복사한 파일 목록"에 `src/components/ui/*.tsx` 항목이 하나 이상 있다(원본 경로가 `design-system/src/components/ui/…`여도 같다).
     - 기록에 1.5.0부터의 설정 프롬프트가 적게 한 규칙, 곧 React·Next.js 컴포넌트는 그 ref로 저장소를 받아 `design-system/src/components/ui/<name>.tsx`를 `@/components/ui`에 복사한다는 문장이 있다.

     둘 다 없고, 지금 판이 1.5.0보다 낮거나 OLD 없이 계속하면 위 컴포넌트를 모두 "shadcn에서 받은 파일"로 표시한다. OLD는 이 파일들의 원본이 아니다. 5번 표는 그대로 쓰되, 9번에서 합치기를 권하지 않는다. 둘 다 없더라도 지금 판이 1.5.0 이상이고 OLD가 있으면 OLD가 이 파일들의 원본이므로, 따로 표시하지 않고 5번 표와 9번의 보통 선택지를 그대로 쓴다.
   - React·Next.js 보조 파일: 프로젝트의 `lib` 폴더(`aliases.lib`, 보통 `src/lib/`)의 `dw-locale.tsx` · `dw-messages.ts` · `dw-date.ts` · `utils.ts`는 `<OLD>/src/lib/`·`<NEW>/src/lib/`의 같은 이름과, `hooks` 폴더(`aliases.hooks`, 보통 `src/hooks/`)의 `use-mobile.ts`는 `<OLD>/src/hooks/`·`<NEW>/src/hooks/`의 같은 이름과 짝이다. 프로젝트에 있는 것만 넣는다. 없는 것은 7번에서 필요하면 넣을 목록에 올린다.
   - 기록에 복사한 파일 목록이 있으면 그 파일도 넣는다. 목록에 적힌 원본 경로가 `design-system/`으로 시작하면 그 부분을 떼고 `<OLD>`·`<NEW>` 뒤에 붙인다. 예: `design-system/src/components/ui/dialog.tsx`는 `<OLD>/src/components/ui/dialog.tsx`, `design/tokens.css`는 `<OLD>/design/tokens.css`다. 목록에 있지만 프로젝트에 더는 없는 파일은 프로젝트가 지운 것이다. 비교하지 않고 되살리지 않으며, 10번 보고에 적는다.
   - `docs/design-reference/`는 넣지 않는다. 6번에서 따로 처리한다.

5. 파일마다 세 판을 비교해 아래 표에서 처음 맞는 줄대로 처리를 정해줘. 같은지는 `cmp -s <가> <나>`로 본다(내용이 한 글자라도 다르면 다르다).

   | 경우 | 처리 |
   | --- | --- |
   | 프로젝트 = NEW | 이미 새 판이다. 그대로 둔다 |
   | 프로젝트 = OLD, NEW에 있음 | 프로젝트에서 고치지 않았다. NEW로 바꿀 목록에 넣는다. 묻지 않는다 |
   | 프로젝트 = OLD, NEW에 없음 | 새 판에서 빠진 파일이다. 프로젝트에서 그 파일 이름을 부르는 곳이 없으면 지울 목록에 넣고, 있으면 남길 목록에 넣어 보고에 적는다. 묻지 않는다 |
   | OLD = NEW (프로젝트만 다름) | 새 판이 바꾸지 않았다. 프로젝트의 수정을 그대로 둔다. 묻지 않는다 |
   | 프로젝트에 없음, NEW에만 있음 | 새 파일이다. 4번의 실행 파일이면 넣을 목록에 올리고, 보조 파일이면 7번에서 필요할 때만 올린다 |
   | 프로젝트 ≠ OLD, OLD에 있고 NEW에 없음 | 프로젝트에서 고친 파일이 새 판에서 빠졌다. "고친 파일" 목록에 넣는다. 고를 수 있는 것은 남기기와 지우기뿐이다 |
   | OLD 없이 계속, 프로젝트에 있고 NEW에 없음 | 기록의 복사한 파일 목록에 있지만 새 판에 없는 파일이다. "고친 파일" 목록에 넣는다. 고를 수 있는 것은 남기기와 지우기뿐이다 |
   | 그 밖 (프로젝트 ≠ OLD이고 OLD ≠ NEW, OLD에 없는데 프로젝트 ≠ NEW, OLD 없이 계속하는 경우의 프로젝트 ≠ NEW) | 덮어쓰지 않는다. "고친 파일" 목록에 넣는다 |

   - 파일마다 어느 줄에 해당했는지 적어 둔다. 10번 보고에 쓴다.
   - "고친 파일"은 9번에서 한 번에 묻는다.

6. `docs/design-reference/`가 있으면 9번에서 안의 내용을 모두 지우고 `<NEW>/design/` 전체를 복사한다. 이 폴더는 프로젝트에서 고치지 않는 참고 문서이므로 파일마다 비교하지 않고 통째로 바꾼다. 다만 바꾸기 전에 사라질 내용을 찾는다.
   - OLD가 있으면 `diff -rq docs/design-reference <OLD>/design`, OLD 없이 계속하면 `diff -rq docs/design-reference <NEW>/design`으로 본다. OLD가 있을 때는 `docs/design-reference/`에만 있는 파일과 내용이 다른 파일, OLD가 없을 때는 `<NEW>/design/`에 없는 파일이 "참고 문서에서 달랐던 파일"이다.
   - 달랐던 파일이 있으면 9번 질문에 넣는다. 고를 수 있는 것은 (가) 통째로 바꾸기(달랐던 파일은 버린다. 프로젝트에서 정한 내용이면 규칙 파일로 옮기라고 알린다), (나) 달랐던 파일만 그대로 두고 나머지를 새 판으로 바꾸기다.
   - 폴더가 없으면 만들지 않는다.

7. 고른 경로가 새 판에서 필요로 하는 파일과 패키지를 정해 목록에 적어줘. 연결 방법의 정본은 `<NEW>/design/design.md` 14장이다(React·Next.js 14.1, 서버 템플릿 웹 14.2, 웹이 아닌 환경 14.3). 이 글에 다시 적지 않으니 14장을 읽고 따른다.
   - React·Next.js: `<NEW>/src/lib/dw-locale.tsx`와 `<NEW>/src/lib/dw-messages.ts`가 있으면(1.5.0부터) 프로젝트의 `lib` 폴더에 넣을 목록에 올린다. 5번 결과 `ui` 폴더에 `calendar.tsx`나 `date-picker.tsx`가 있으면 `<NEW>/src/lib/dw-date.ts`도 올리고 `date-fns`를 설치할 패키지 목록에 올린다.
   - NEW에서 가져올 파일(5번에서 NEW로 바꾸는 파일, 위에서 넣는 파일, 9번에서 사용자가 합치기나 새 판을 고른 파일)마다 `import`를 확인한다. `@/components/ui/*`·`@/lib/*`·`@/hooks/*` 중 프로젝트에 없는 파일은 `<NEW>`의 같은 파일을 넣을 목록에 올리고, 그 파일의 `import`도 같은 방법으로 확인한다. 이렇게 올린 파일도 5번 표의 "새 파일"로 보고한다. 같은 경로에 내용이 다른 프로젝트 파일이 있으면 덮어쓰지 않는다. 9번 질문 전에 찾았으면 "고친 파일" 목록에 넣는다. 9번에서 답을 받은 뒤의 확인에서 찾았으면 다시 묻지 않는다. 프로젝트 파일을 그대로 두고 10번 보고의 "남긴 것"에 넣어, 사용자가 정해야 한다고 알린다.
   - 가져올 파일이 불러오는 패키지가 프로젝트에 없으면 설치할 패키지 목록에 올린다. 9번에서 프로젝트의 패키지 관리자로 설치하고, 판은 `<NEW>/package.json`에 적힌 범위를 쓴다. 이미 있는 패키지는 그대로 둔다. `<NEW>/package.json`보다 주 버전이 낮아도 올리지 않고, 10번에서 빌드가 깨지면 보고에 적는다.
   - 연결한 파일(전역 CSS, 공통 템플릿)이 14장의 불러오는 순서와 다르면 9번에서 14장대로 맞출 곳으로 적어 둔다. 관련 없는 내용은 그대로 둔다.
   - 웹이 아닌 환경: 플랫폼 코드로 옮긴 값은 자동으로 바꾸지 않는다. `<OLD>/design/tokens.json`과 `<NEW>/design/tokens.json`에서 값이 바뀐 토큰을 골라 9번에서 플랫폼 값에 옮길지 묻는다. OLD 없이 계속하면 `<NEW>/design/tokens.json`과 프로젝트의 플랫폼 값을 비교한다.

8. `<NEW>/CHANGELOG.md`에서 지금 판보다 높고 올릴 판 이하인 절을 읽어줘. 1.2.0까지의 절도 같은 파일에 있다. 화면 동작, 컴포넌트 사용법, 설정 방법이 바뀌어 사용자가 확인하거나 정해야 하는 항목을 골라 둔다. 기록이 한 줄뿐이라 무엇이 바뀌었는지 알 수 없으면 `<NEW>/design/design.md` 14장과 5번에서 바뀐 파일의 차이로 확인한다(예: 1.5.0의 한국어·영어 지원은 14.1의 언어 설정 항목 — 문구 Provider와 클라이언트 컴포넌트가 된 목록).
   - 지금 판이 브랜치나 커밋 값이면 그 상태에 이미 들어 있는 마지막 릴리즈를 기준으로 한다. 기록에 그 버전이 적혀 있으면(예: "design-system 1.4.0 기준") 그 버전보다 높은 절부터 읽는다. 알 수 없으면 가장 최근 릴리즈 세 개의 절을 요약하고, 범위를 알 수 없었다고 보고에 적는다.
   - 올릴 판이 브랜치나 커밋 값이면 `<NEW>/CHANGELOG.md` 맨 위 절까지 읽는다. 그 뒤 릴리즈되지 않은 변경은 CHANGELOG에 없다고 함께 알린다.
   - 빠진 설정 단계는 `<NEW>/design/ai/setup-prompt.md`의 두 단계만 본다. 화면 점검 스킬(`web-design-guidelines`, `ux-heuristics`)을 설치하는 단계와 AI 규칙 문구를 병합하는 단계다. 프로젝트에 그 스킬이 없거나 규칙 문구가 그 단계의 문구와 다르면 9번에서 그 단계를 적용할지 묻는다. 적용하기로 하면 9번에서 그 단계만 그대로 따른다.
   - 설정 프롬프트의 다른 단계(파일 복사, 연결, 기록)는 다시 하지 않는다. 파일은 4~7번이 다룬다.

9. 묻고 반영해줘.
   - 아래 중 하나라도 있으면 한 번에 보여 주고 묻는다. 순서도 이대로다.
     1. 맨 위: 3번에서 OLD 없이 계속한 이유(기록에 ref가 없다 · 태그가 아니다 · 받지 못했다(오류 내용) · 기록에 커밋 값이 없다 · 커밋 값이 기록과 다르다(두 값)).
     2. 커밋하지 않은 변경: 1번에서 적어 둔 변경 중 이번에 바꾸거나 지울 파일, 또는 `docs/design-reference/` 안의 파일이 있으면 그 목록을 보이고, 먼저 커밋할지 그대로 계속할지 묻는다.
     3. "고친 파일" 목록: 파일마다 경로와 한두 줄 요약, 고를 수 있는 것. 요약은 프로젝트가 OLD와 어떻게 다른지, 새 판이 무엇을 바꿨는지다. 서식만 다르면 그렇게 적는다. 고를 수 있는 것은 (가) 합치기: `git merge-file -p <프로젝트 파일> <OLD 파일> <NEW 파일>` 결과를 쓰고 충돌이 나면 충돌 부분을 보여 주고 다시 묻는다, (나) 그대로 두기, (다) 새 판으로 바꾸기(프로젝트 수정을 버린다)다. "shadcn에서 받은 파일"과 OLD 없이 계속한 파일은 (나)와 (다)만 있고, 요약은 프로젝트와 NEW의 차이로 적는다. 새 판에서 빠진 파일은 OLD가 있든 없든 언제나 남기기와 지우기만 있다. 이 규칙이 앞의 (나)·(다) 규칙보다 앞선다. OLD 없이 계속해 목록이 길면 폴더 단위로 묶어 한 번에 고르게 하고, 따로 고를 파일만 따로 적는다.
     4. 6번의 참고 문서에서 달랐던 파일.
     5. 7번의 웹이 아닌 환경 토큰 값, 8번의 빠진 설정 단계와 사용자가 확인할 변경.
   - 안전한 파일(5번 표의 위쪽 다섯 줄)은 묻지 않는다.
   - 답을 받으면 4~8번에서 적어 둔 목록과 사용자가 고른 처리를 반영한다. NEW로 바꾸기, 새 파일(실행 파일, `lib`·`hooks` 파일, 의존 컴포넌트) 넣기, 지우기, 6번의 `docs/design-reference/` 교체, 7번의 연결 파일 맞추기와 패키지 설치를 이때 한다. 사용자가 합치기나 새 판을 고른 파일은 7번의 `import` 확인을 한 번 더 해서 빠진 파일과 패키지도 함께 넣는다. 이 확인에서 넣으려는 파일이 프로젝트에 이미 있고 내용이 다르면 덮어쓰지 않고 다시 묻지도 않는다. 그 파일은 그대로 두고 10번 보고의 "남긴 것"에 사용자가 정해야 할 파일로 적는다.
   - `docs/design-system.md`를 고친다. 저장소 주소는 `https://github.com/daewoong-axtf/ax-kit`, ref는 올릴 판, 커밋 값은 NEW의 값으로 바꾸고, 날짜는 오늘로 바꾼다(없으면 넣는다). 이번에 바꾼 파일, 새로 넣은 파일, 지운 파일, 설치한 패키지, 남긴 파일과 이유를 "업그레이드 <지금 판> → <올릴 판>" 절로 덧붙인다. `<NEW>/design/ai/setup-prompt.md`의 기록 단계가 적으라는 항목 중 기록에 없는 것(예: React·Next.js의 컴포넌트를 받는 방법, 점검 스킬)을 채운다. 9번 질문에서 사용자가 적용하지 않기로 한 설정 단계는 적용하지 않았다고 적는다. 나머지 내용은 유지한다.
   - 1번에서 찾은 AI 규칙 파일에 예전 저장소 이름(`daewoong-design-system`, `daewoong-ax-standards`), 예전 판이나 ref, 이 컴퓨터에만 있는 로컬 경로(예: `/Users/<이름>/…`에 받아 둔 저장소)가 있으면 고친다. 이름은 `ax-kit`, 판은 올릴 판으로 바꾸고, 로컬 경로는 지우고 `docs/design-system.md`에 적힌 ref로 저장소를 받으라는 말로 바꾼다. 규칙의 나머지 내용은 유지한다.

10. 검증하고 보고해줘.
   - 프로젝트에서 쓸 수 있는 타입·린트·테스트·빌드 검사를 실행한다. 화면이 있으면 라이트·다크 모드에서 확인한다.
   - 이번에 만든 OLD·NEW 임시 폴더를 모두 지운다. OLD를 쓰지 않은 이유가 무엇이든(받다가 실패했다, 커밋 값이 달랐다 등) 만들어 둔 OLD 폴더도 여기서 함께 지운다.
   - 보고에 적는 것: 지금 판 → 올릴 판, OLD 없이 계속했으면 그 이유, NEW로 바꾼 파일, 그대로 둔 파일과 이유(5번 표의 어느 줄인지), 남긴 것(사용자가 정해야 할 파일 포함), 기록에는 있지만 프로젝트가 지운 파일, 사용자가 고른 처리, 새로 넣은 파일, 지운 파일, 설치한 패키지, 8번에서 알린 변경, 고친 기록·규칙 파일, 검증 결과. 같은 줄에 해당한 파일이 많으면(예: `fonts/`·`icons/`) 폴더 단위로 묶고 개수를 적는다.
   - 검사가 하나라도 실패했으면 끝났다고 말하지 않는다. 실패한 검사와 원인을 적는다.

지킬 것.
- 어느 단계에서 멈추든 받은 임시 폴더(OLD·NEW, 받다가 실패한 폴더 포함)는 지우고 멈춘다.
- 프레임워크를 바꾸거나 주요 의존성의 주 버전을 올리지 않는다.
- 생성 파일(`tokens.css`, `dw-messages.ts`, `js/components.js` 등)은 프로젝트에서 손으로 고치지 않는다. 새 판의 파일로 바꾸거나 그대로 둔다.
- 복사한 컴포넌트의 구조·변형 이름·색 클래스를 고치지 않는다.
- 기존 화면을 다시 디자인하지 않는다. 새 판에 맞추는 데 필요한 만큼만 바꾼다.
- 복사한 문서에 나오는 `pnpm build:*` 명령은 디자인 시스템 저장소 전용이다. 프로젝트에 추가하지 않는다.
- 사용자가 요청하지 않으면 커밋하거나 푸시하지 않는다.
- 묻는 것은 맨 위에 적은 경우뿐이다.
