# write-prd

노션에 있는 팀 기준을 정본으로 삼아 PRD를 쓴다. 기준은 스킬에 복사해 두지 않고 **매번 노션에서 읽는다** — 기준 페이지가 고쳐지면 다음 PRD부터 바로 반영되게 하려는 것이다.

## 노션 위치

| 무엇 | ID / URL |
| --- | --- |
| PRD 작성 기준 (정본) | `41b3d273-ae9b-80f4-b9dc-fcf85ff1ccb7` |
| AX PM 문서 (쓰는 규칙 3절) | `41b3d273-ae9b-80b5-9ec4-f374a994682d` |
| AX PRD 문서 DB (저장 위치) | `collection://56e88947-9909-4a3c-8d22-b9ae32026c56` |

ID로 못 찾으면 `notion-search`로 제목("PRD 작성 기준", "AX PRD 문서")을 찾는다. 그래도 못 읽으면 **기억으로 대신 쓰지 말고** 멈춰서 사용자에게 알린다.

## 절차

### 1. 기준 읽기
`notion-fetch`로 위 두 페이지를 읽는다. 같은 대화에서 이미 읽었더라도 PRD를 새로 쓸 때마다 둘 다 다시 읽는다(그사이 고쳐졌을 수 있다). 여기서 뽑아 쓸 것:
- 핵심 구성요소 표 (항목, 답해야 할 질문, 필수 여부)
- 품질 평가 차원
- 기능 요구사항 예시 형식 (FR 번호, 사용자 상황, 기능 요구사항, 업무 규칙, Acceptance Criteria, 추가 결정 필요)
- Definition of Ready 조건
- AX PM 문서의 쓰는 규칙 (확정/초안/미결정 구분, 담당자·확인 시점, 정본 링크·기준일, 목차와 제목 번호, 민감정보 금지)

아래 단계에서 말하는 "구성요소", "품질 차원"은 모두 **이번에 읽은 기준 페이지의 것**이다. 기준이 바뀌었으면 바뀐 대로 따른다.

### 2. 재료 모으기
- 노션 URL(티켓, 회의록, 기존 문서)을 받으면 전부 `notion-fetch`로 읽는다. 티켓 본문에 링크된 회의록·시안도 PRD에 필요하면 따라가 읽는다.
- 붙여넣은 텍스트나 로컬 파일이 있으면 그것도 읽는다.
- 재료를 구성요소별로 나눠 보고, **필수 항목 중 근거가 없는 것만** 추린다.
- 재료에 "보류", "후속 논의", "미정"으로 이미 기록된 것은 묻지 않는다. 바로 10번 항목(미결정 사항)으로 보내고, 재료에 나온 담당자와 시점을 그대로 옮긴다.
- 그래도 남는 것 중 **결정할 사람도 시점도 알 수 없는 필수 항목만** 초안 전에 한 번에 묶어 질문한다(최대 5개, 한 질문에 하나씩). 이런 항목이 없으면 질문 없이 초안으로 간다. 사용자가 모른다고 하면 지어내지 말고 10번 항목으로 보낸다.
- 재료가 거의 없으면(한두 줄 아이디어) 인터뷰로 시작한다: 문제 → 사용자·상황 → 목표·측정 → 범위·제외 → 핵심 흐름 순서.

### 3. 초안 쓰기
문서 맨 위:
```
작성자: <작성자> · 작성일: <YYYY-MM-DD> · 상태: 초안
근거: <읽은 티켓·회의록 링크와 기준일>
```
그다음 목차, 그리고 기준의 구성요소 순서대로 `## 1.` `## 2.` … 제목 번호를 붙여 쓴다.

**목차와 섹션 제목은 한글로 쓴다.** 기준 페이지의 영문 구성요소명은 아래처럼 옮긴다. 기준에 새 항목이 생기거나 이름이 바뀌면 같은 방식으로 한글로 옮기고, 순서와 번호는 기준을 따른다.

| 기준 구성요소 | 섹션 제목 |
| --- | --- |
| Context & Problem | 배경과 문제 |
| Goals & Success Metrics | 목표와 성공 지표 |
| Users & Use Cases | 사용자와 사용 사례 |
| Scope & Non-goals | 범위와 제외 범위 |
| Functional Requirements | 기능 요구사항 |
| UX & User Flows | 사용자 흐름 |
| Data & Business Rules | 데이터와 업무 규칙 |
| Non-functional Requirements | 비기능 요구사항 |
| Acceptance Criteria | 수용 기준 |
| Dependencies & Open Questions | 의존성과 미결정 사항 |

쓰는 규칙:
- **기능 요구사항은 기준 페이지의 FR 예시 형식을 그대로 따른다.** `FR-001`부터 번호를 매기고, 항목마다 사용자 상황 · 기능 요구사항 · 업무 규칙 · Acceptance Criteria · 추가 결정 필요를 둔다.
- Acceptance Criteria는 정상 동작만 쓰지 않는다. 빈 결과, 경계값, 권한 밖 접근, 외부 장애·재시도 중 해당하는 것을 넣는다.
- "빠르게", "쉽게", "적절히"처럼 해석이 갈리는 말은 쓰지 않는다. 수치가 없으면 숫자를 지어내지 말고 `미정 (결정: 담당자, 시점)`으로 둔다.
- 재료에 없는 사실, 수치, 일정, 담당자는 만들지 않는다. 추정이면 `(추정)`, 제안이면 `(제안)`을 붙인다.
- "해당 시 필수" 항목이 정말 해당 없으면 지우지 말고 `해당 없음 — 이유`를 한 줄 쓴다.
- 화면 세부, API·DB 설계, 테스트 케이스 전체는 PRD에 넣지 않는다(기준 3절의 문서 구분). 필요하면 별도 문서로 링크만 건다.
- 미결정 사항은 표로: `질문 | 영향 범위 | 결정할 사람 | 결정 시점`.
- 개인정보 · 비밀번호 · 키 · 내부 접속정보는 쓰지 않는다. 재료에 있어도 뺀다.

### 4. 자체 점검
초안 끝에 `## 부록. 품질 점검` 섹션을 붙인다. 기준의 품질 차원마다 한 줄씩:

| 차원 | 판정 (충족 / 부분 / 미흡) | 근거 · 보완할 점 |

이어서 Definition of Ready를 체크리스트로 적고, 개발 착수 가능 여부를 한 줄로 판정한다. 미결정 사항이 남아도 구현에 영향이 없거나 결정자·시점이 정해졌으면 착수 가능으로 본다.

`미흡`이 나온 차원은 재료로 고칠 수 있으면 고치고 다시 점검한다. 재료가 없어서 못 고치는 것만 남긴다.

### 5. 확인 후 노션에 저장
1. 초안 전체를 작업 폴더의 `prd-drafts/<티켓 ID 또는 과제명>-PRD.md`에 저장하고, 채팅에는 그 파일 링크와 요약을 보여준다: 제목, FR 개수, 미결정 사항 개수, 품질 점검 결과, 재료에서 찾은 불일치, 사용자가 확인할 질문. 본문 전체를 채팅에 붙이지 않는다.
2. 사용자가 저장하라고 하면 DB 스키마를 `notion-fetch`(`collection://...`)로 다시 읽고 속성 이름을 맞춘다(바뀌었을 수 있음).
3. 두 번에 나눠 만든다. 본문을 `notion-create-pages`의 `pages` 배열에 넣으면 한글이 `\uXXXX`로 이스케이프되어 생성이 몇 배 느려지기 때문이다.
   - 먼저 `notion-create-pages`로 **속성만 넣고 본문은 비운** 페이지를 만든다.
   - 이어서 `notion-update-page`의 `replace_content`로 `new_str`에 본문 전체를 넣는다.

   속성과 본문:
   - `문서`: `<과제명> PRD`
   - `티켓 · 과제` / `티켓 · 과제 제목`: 근거 티켓이 있으면 그 URL과 제목
   - `원본 문서` / `원본 문서 제목`: 주 재료가 된 회의록·문서가 있으면 그 URL과 제목
   - `비고`: `write-prd 초안 · <작성일>` 과 남은 미결정 개수
   - 본문: 로컬 초안 전체. 단, 노션에 맞게 두 가지를 바꾼다 — 맨 위 `#` 제목 줄은 빼고(제목은 `문서` 속성), `- [~]` 같은 부분 체크는 `- [ ] … — 부분: <이유>`로 쓴다.
4. 만든 페이지 링크를 사용자에게 준다. 이후 수정은 노션 페이지가 정본이다. 로컬 초안은 그대로 둔다.

### 기존 PRD 점검 요청일 때
1단계 후, 받은 PRD를 읽고 4단계 점검표만 만들어 보여준다. 고쳐 달라고 하면 고친 본문은 원본을 덮어쓰지 말고, 바꾼 내용을 보여준 뒤 사용자가 고른 방식(원본 수정 또는 새 페이지)으로 저장한다.
