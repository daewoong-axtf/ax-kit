- 기준일: 2026-11-24
- 용도: 코딩 에이전트로 업무용 웹앱을 새로 만들거나 이미 만든 앱에 적용할 때 넣는 규칙 파일 원문. 배포 시 Claude Code는 `CLAUDE.md`, 그 외 도구는 `AGENTS.md`로 이름을 바꿔 앱 폴더 맨 위에 둔다.

## 작업 방식

이 프로젝트는 회사 업무용 웹앱이다. 코드를 작성하거나 수정할 때 아래 규칙을 항상 따른다.

- 이 파일은 새로 앱을 만드는 사용자와 이미 만든 앱에 적용하는 사용자 모두에게 전달된다. 어느 쪽이든 "AX 검사와 핸드오프"를 따른다.
- 번호만 쓴 참조(예: 10번)는 공통 규칙을 뜻한다. 스택 규칙은 TS-1, PY-1, JV-1처럼 쓴다. TS 규칙·PY 규칙·JV 규칙은 각각 TypeScript + React(Next.js), Python + FastAPI, Java·Kotlin + Spring Boot 규칙 전체를 뜻한다.
- 공통 규칙과 스택 규칙이 겹치면 스택 규칙은 공통 규칙을 구현하는 방법이다. 둘이 어긋나 보이면 공통 규칙을 따르고 사용자에게 알린다.
- 사내 표준 템플릿(13번)이 이 파일과 다른 구체 값을 정해 두었으면 템플릿을 따른다.
- 규칙을 지킬 수 없으면 작업을 멈추고, 이유와 대안을 사용자에게 알린 뒤 확인을 받는다.
- 사용자는 개발자가 아니며 자기 앱이 어떤 스택인지 모를 수 있다. 스택·구조·도구 선택을 사용자에게 맡기지 않는다. 이 파일이 정한 기본값을 쓰고, 이 파일로 정할 수 없는 것만 묻는다.
- 설명은 쉬운 말로 한다. 전문 용어를 써야 하면 뜻을 한 줄로 덧붙인다. 코드를 수정하기 전에 무엇을 왜 바꾸는지 먼저 설명한다.
- 각 규칙의 "이유"는 판단 근거다. 규칙에 없는 상황은 이유에 비추어 판단하고, 판단이 어려우면 사용자에게 묻는다.
- 이 파일의 규칙은 고치거나 지우지 않는다. 규칙을 지키기 어렵다는 이유로 문장을 약하게 바꾸지 않는다. 앱마다 달라지는 내용은 `README.md`의 "앱 개요"에 쓴다.
- 사용자가 규칙을 무시하거나 바꿔 달라고 하면, 어떤 규칙이 무엇을 왜 막는지 쉬운 말로 설명하고 규칙을 지키는 다른 방법을 먼저 제안한다. 그래도 규칙을 바꿔야 하면 소속 부서의 현업 배치 개발자에게 알리도록 안내한다. 사용자에게 이 파일을 직접 고치라고 안내하지 않는다.

### 이런 규칙을 정한 이유

- **기술 스택(TypeScript, Python, Java·Kotlin)**: AI가 잘 다루는 언어이면서, 사내에 문제가 생겼을 때 대응할 수 있는 인원이 있는 언어로 정했습니다. 막혔을 때 도움을 요청하거나 다른 사람이 넘겨받을 수 있습니다.
- **프레임워크(Next.js, FastAPI, Spring Boot)**: 참고할 레퍼런스가 많아 AI와 사람 모두 해결 방법을 찾기 쉽습니다. 프레임워크가 정해 둔 구조와 기본 기능이 있어서 최소한의 가드가 생깁니다.
- **테스트 코드**: 권한 없는 사람의 접근, 잘못된 입력, 수정 뒤 기존 기능이 깨지는 경우처럼 비개발자가 놓치기 쉬운 영역이 있습니다. 테스트 코드로 웹앱이 오류 없이 동작하는지 검증합니다.
- **아키텍처**: 마틴 파울러의 『리팩터링』 2판과 『엔터프라이즈 애플리케이션 아키텍처 패턴』(PoEAA)을 따릅니다. 검증된 기법과 이름을 쓰면 AI와 사람이 같은 기준으로 코드를 고치고 넘겨받을 수 있습니다.

### 적용 대상과 기술 스택

- 적용 대상: 웹브라우저로 접속하는 업무용 웹앱.
- 적용 제외: 엑셀 매크로, 내 PC에서만 실행하는 스크립트, 데스크톱 앱, 예약 실행 작업, 연구·데이터 분석용 Python 코드(노트북·분석 스크립트).

웹앱은 아래 스택만 사용한다. 런타임 버전은 2026-10-30 기준 최신 LTS·안정 버전이다.

| 구분                       | 표준                                                                                  | 세부 규칙    |
| -------------------------- | ------------------------------------------------------------------------------------- | ------------ |
| 프론트엔드                 | TypeScript + React(Next.js App Router), Node.js 26 LTS                                | TS 규칙      |
| 프론트엔드(FastAPI 일체형) | FastAPI가 제공하는 HTML + JavaScript. 프론트엔드와 백엔드를 나누지 않는 앱에서 사용   | PY-8         |
| 프론트엔드(Java 계열)      | Spring Boot가 제공하는 Thymeleaf 화면. JV 규칙을 쓰는 앱에서만 사용                   | JV-8         |
| 백엔드(기본)               | Python 3.15 + FastAPI                                                                 | PY 규칙      |
| 백엔드(Java 계열)          | Java 25 LTS 또는 Kotlin 2.4 + Spring Boot                                             | JV 규칙      |
| DB                         | PostgreSQL(운영 기준). SQLite는 로컬 개발에서만 사용                                  | 13번         |
| 배포 단위                  | 프론트엔드·백엔드 컨테이너 각 1개(FastAPI + HTML, Spring Boot + Thymeleaf 구조는 1개) | 13번         |

- 런타임은 위 표의 버전을 쓰고, 그 버전 안에서 최신 패치를 설치한다. 최신 패치는 AI가 기억하는 버전이 아니라 공식 사이트(nodejs.org, python.org, kotlinlang.org, Java는 사용하는 JDK 배포처)나 설치 도구로 확인한다. 표의 버전을 지원하지 않는 라이브러리가 있으면 임의로 버전을 낮추지 말고 사용자에게 알린다. 확인할 수 없으면 사용자에게 알리고 묻는다.
- 설치한 버전은 패치까지 정확한 값으로 고정한다(고정 위치는 TS-1, PY-1, JV-1). 보안 패치는 설치한 버전에 저절로 적용되지 않는다. 새 대화에서 작업을 시작할 때 같은 버전 안의 새 패치(예: 26.13.0 → 26.13.1)가 있는지 확인하고, 있으면 올린 뒤 사용자에게 알린다. 다른 메이저·마이너 버전으로 올리는 것은 사용자 확인을 받는다.
- 표의 버전이 지원 종료(EOL)되면 보안 패치가 나오지 않는다. 작업 시작 시 지원 종료일을 확인하고, 지났거나 6개월 안에 다가오면 사용자에게 알린다. 표의 버전을 바꾸는 것(다음 LTS로 이동 등)은 이 규칙 파일이 갱신될 때만 한다.
- lint·포맷·타입 검사 규칙을 끄거나 예외 주석으로 우회하지 않는다. 우회가 꼭 필요하면 이유를 사용자에게 알리고 확인을 받는다.

### 스택 판별

사용자에게 스택을 묻지 않는다. 파일을 보고 판별하고, 결과를 `README.md`의 "앱 개요"에 기록한다.

| 발견한 것                                                 | 판별                      | 적용                |
| --------------------------------------------------------- | ------------------------- | ------------------- |
| `package.json`에 `react` 또는 `next`                      | TypeScript + React        | TS 규칙             |
| `pyproject.toml`·`requirements.txt`와 `fastapi`           | Python + FastAPI          | PY 규칙             |
| `react`·`next`가 없고 FastAPI가 HTML 화면을 제공          | FastAPI + HTML            | PY 규칙(PY-8 포함)  |
| `build.gradle.kts`·`build.gradle`·`pom.xml`와 Spring Boot | Java·Kotlin + Spring Boot | JV 규칙             |
| `react`·`next`가 없고 Spring Boot에 `thymeleaf` 의존성    | Spring Boot + Thymeleaf   | JV 규칙(JV-8 포함)  |

- 프론트엔드와 백엔드가 한 저장소에 있으면 폴더마다 해당 스택 규칙을 적용한다.
- 새 프로젝트는 화면이 표·입력 폼 위주면 FastAPI + HTML(PY-8)로 만들고, 화면 상호작용이 많으면 프론트엔드를 TS 규칙, 백엔드를 PY 규칙으로 만든다. 사용자에게 고르게 하지 않고 에이전트가 정해 `README.md`의 "앱 개요"에 기록한다. JV 규칙은 사내 표준 템플릿이 Java 계열을 지정했거나, 이미 Java·Kotlin으로 만든 백엔드에 기능을 붙일 때만 쓴다.
- 표준 밖 스택(Streamlit, Gradio, Flask, Django, Express, 바닐라 JS(PY-8의 FastAPI + HTML 구조 제외), JSP, PHP 등)이면 표준 스택으로 옮기는 대상이다. 화면은 TS 규칙으로, 서버 로직은 PY 규칙으로 옮긴다. 화면이 표·입력 폼 위주면 FastAPI + HTML(PY-8)로 옮겨도 된다. 기존 서버가 Java·Kotlin이면 서버 로직은 JV 규칙으로 옮기고, 화면은 JV-8로 옮겨도 된다. 옮기기 전에 아래 "규격화와 리팩토링" 순서로 계획을 세우고, 무엇이 바뀌는지 쉬운 말로 설명한 뒤 확인을 받는다. 옮기기 전에도 보안 규칙(1~17번)은 그대로 적용한다.
- 표준 밖 스택으로 새로 만들지 않는다. 사용자가 요청해도 표준 스택으로 만든다.

### 작업 시작 전 확인

새 프로젝트를 시작하거나 이 파일을 처음 적용할 때, 아래 항목이 `README.md`에 없으면 코드를 쓰기 전에 사용자에게 묻는다. 답은 `README.md`의 "앱 개요"에 기록하고, 이후 대화에서는 README를 먼저 읽는다.

1. 앱의 목적: 어떤 업무의 무엇을 줄이려는가
2. 사용자 범위: 나 / 팀 / 부서 / 전사
3. 다루는 데이터: 공개 정보 / 사내 자료 / 개인정보(4번 기준)
4. 연결할 외부 서비스·사내 시스템
5. 실행·배포 위치: 내 PC / 사내 서버(앱허브) / 외부 배포 서비스
6. 앱을 소유하는 팀과 유지보수 담당자

답에 따라 다음을 먼저 한다.

- 3번이 개인정보면 4번 규칙을, 4번에 외부 AI가 있으면 2번 규칙을 먼저 적용한다.
- 2번이 팀 이상이면 기능을 만들기 전에 10번의 권한 표를 만든다.

### AX 검사와 핸드오프

앱이 이 규칙을 얼마나 지키는지 점수로 검사하고, 핸드오프 기준을 채우면 AXTF에 넘긴다. 핸드오프 기준은 필수 항목이 모두 100점이고 권장 점수가 90점 이상인 것이다.

**필수 항목은 무조건 모두 통과해야 한다.** 필수 항목이 하나라도 100점이 아니면 총점과 권장 점수가 아무리 높아도 통과가 아니고, 핸드오프도 완료 안내도 하지 않는다. 사용자가 요청해도 필수 미달을 면제하거나, 이유를 적어 남기거나, 다른 항목의 점수로 대신하지 않는다. 세부 기준이 모두 해당 없음인 필수 항목은 그 근거를 리포트에 적으면 통과로 본다.

| 상황              | 판단 기준                                                      | 검사 시점                                                        |
| ----------------- | -------------------------------------------------------------- | ---------------------------------------------------------------- |
| 새 앱             | 앱 코드가 아직 없다                                            | 규칙대로 만들고, 첫 기능을 완성했을 때와 공유·배포 전에 검사한다 |
| 기존 앱           | 앱 코드가 있고 `reports/`에 리포트가 없다                      | "작업 시작 전 확인"을 마친 뒤, 코드를 고치기 전에 검사한다       |
| 사용자 요청       | "검사해줘", "규칙 파일 기준으로 점검해줘" 등                   | 바로 검사한다                                                    |
| 마이그레이션 요청 | "안전 규칙 준수하도록 해줘", "규칙에 맞게 마이그레이션해줘" 등 | 바로 검사하고 "마이그레이션 대화"를 끝까지 따른다                |

#### 채점 방법

- 검사는 코드를 고치지 않고 리포트 파일만 만든다.
- 채점 항목은 표준 스택 적합 여부("적용 대상과 기술 스택", "스택 판별"), 개발 순서, 공통 1~17번, 해당 스택 규칙(TS-n, PY-n, JV-n)이다. 각각을 한 항목으로 센다. 표준 밖 스택이면 옮겨 갈 스택 규칙으로 채점한다.
- 항목마다 규칙의 요구사항 중 코드·설정·문서·테스트로 확인할 수 있는 것을 세부 기준으로 삼는다. 세부 기준의 결과는 지킴 / 위반 / 확인 불가 / 해당 없음 중 하나다.
- 지킴은 근거(파일:줄 또는 명령 실행 결과)가 있을 때만 준다. lint·포맷·타입 검사·테스트·취약점 점검은 실제로 실행한 결과로 판단한다. 확인 불가는 위반과 같이 0점이다.
- 항목은 필수와 권장으로 나눈다.

| 구분 | 항목                                                                   | 가중치 | 미달일 때                                    |
| ---- | ---------------------------------------------------------------------- | ------ | -------------------------------------------- |
| 필수 | 공통 1·2·3·4·6·7·9·10·12·16번                                          | 2      | 핸드오프할 수 없다                           |
| 권장 | 표준 스택 적합 여부, 개발 순서, 공통 5·8·11·13·14·15·17번, 해당 스택 규칙 | 1      | 점수만 깎이고, 남기는 이유를 리포트에 적는다 |

- 세부 기준(문항) 하나의 배점은 `100 ÷ (전체 − 해당 없음)`이다. 항목 안의 문항은 배점이 모두 같다. 지킴은 배점을 다 받고, 위반과 확인 불가는 0점이고, 해당 없음은 전체 개수에서 뺀다. 부분 점수는 없다.
- 항목 점수는 `지킴 ÷ (전체 − 해당 없음) × 100`이다. 세부 기준이 모두 해당 없음인 항목은 총점에서 뺀다.
- 총점은 `(필수 항목 점수의 합 × 2 + 권장 항목 점수의 합) ÷ (필수 항목 수 × 2 + 권장 항목 수)`이고 소수점은 버린다. 같은 구분의 항목은 문항 수와 상관없이 비중이 같다. 계산에는 소수점을 버리기 전의 항목 점수를 쓰고, 리포트 표에만 버린 값을 적는다. 세부 기준이 하나라도 미달이면 100점이 아니다.
- 필수 점수와 권장 점수는 각각 해당 항목 점수의 평균이고 소수점은 버린다. 총점과 함께 리포트에 적는다.
- 문항 하나가 총점에 주는 값은 `문항 배점 × 항목 가중치 ÷ (필수 항목 수 × 2 + 권장 항목 수)`다. 문항이 적은 항목일수록, 필수 항목일수록 한 문항의 비중이 크다. 예: 필수 9개, 권장 16개일 때 문항 2개인 필수 항목의 한 문항은 약 2.9점, 문항 8개인 권장 항목의 한 문항은 약 0.4점이다.
- 재검사 때는 이전 리포트의 세부 기준을 그대로 쓴다. 기준을 바꾸면 이유를 리포트에 적는다. 채점 방식이 바뀌면 이전 점수를 새 방식으로 다시 계산해 적는다. 점수를 올리려고 세부 기준을 줄이거나, 해당 없음으로 바꾸거나, 항목의 필수·권장 구분을 바꾸지 않는다.

> 리팩토링을 하지 않으면 AXTF에서 SSO, 호스팅을 이용하는 것이 적합하지 않을 수 있어요. 리포트는 axtf-support@daewoong.co.kr로 전달해주세요.

#### 마이그레이션 대화

사용자가 앱을 이 규칙에 맞춰 달라고 하면, 첫 리포트부터 총점 80점 이상이 될 때까지 에이전트와 사용자가 질문과 대답을 주고받으며 끝까지 진행한다. 검사만 하고 멈추거나, 다음에 할 일을 사용자가 찾게 두지 않는다. 80점은 중간 목표일 뿐 통과가 아니다. 통과하려면 필수 항목을 모두 100점으로 채워야 한다.

1. 검사한다. 첫 리포트를 만들고, 이 요청을 리팩토링 시작 동의로 본다.
2. 코드를 고치기 전에 현재 점수와 80점까지의 순서를 알린다. 표의 "필요한 것"에는 없음 / 대답 / 허락 / 외부 확인 중 해당하는 것을 적고, 대답이나 허락이 무엇인지 적는다.

   ```txt
   지금 NN점입니다. 80점을 넘기려면 아래 순서로 진행합니다. 순서마다 제가 드리는 질문에 대답해 주시고, 허락이 필요한 일은 허락해 주세요.

   | 순서 | 할 일 | 필요한 것 | 예상 총점 |
   ```

3. 순서는 안전망 테스트("테스트가 없는 프로젝트"), 대답·허락 없이 할 수 있는 일, 대답·허락이 필요한 일, 외부 확인이 필요한 일로 잡는다. 같은 단계에서는 총점을 많이 올리는 일을 먼저 하고, 같으면 필수 항목을 먼저 한다.
4. 순서대로 진행한다. 코드 수정은 "리팩토링"의 1~4번을 따른다. 대답이나 허락이 필요한 순서에 오면 멈추고 질문한다.
   - 한 번에 한 결정만 묻는다. 무엇을 묻는지, 왜 필요한지, 답하면 몇 점이 오르는지, 에이전트의 추천 답을 쉬운 말로 함께 적는다.
   - 시작 동의는 다른 허락을 대신하지 않는다. 큰 변경 계획, 라이브러리 설치와 버전 변경, 되돌리기 어려운 작업, 실행 경로 변경은 그때마다 허락을 받는다.
   - 사용자가 답을 모르면 누구에게 무엇을 물어야 하는지 알려 주고, 외부 확인으로 표시한 뒤 다음 순서로 넘어간다.
   - 권한 표, 보관 기간, 공개 범위, 외부 AI 승인처럼 사용자나 담당자가 정할 내용을 에이전트가 추측해 채우지 않는다.
5. 순서를 하나 마칠 때마다 테스트 결과와 커밋을 확인하고, 점수 변화와 남은 순서를 알린다(예: `78점 → 80점, +2점. 다음은 3번 질문입니다`). 받지 못한 대답은 `README.md`의 "표준 적용 현황"에 적어 새 대화에서 이어 간다.
6. 예상 총점이 80점 이상이면 다시 검사해 새 리포트를 만든다. 예상 점수만으로 80점을 넘겼다고 말하지 않는다. 80점에 못 미치면 2번으로 돌아가 남은 순서를 다시 알린다.
7. 80점을 넘기면 아래 문장으로 알린다. 첫 리포트가 이미 80점 이상이면 2~6번을 건너뛰고 이 문장으로 알린다.

   > NN점으로 1차 목표인 80점을 넘겼지만 이 점수만으로는 통과가 아닙니다. 리포트는 `reports/...-ax-검사-리포트.md`입니다. 필수 항목은 모두 100점이어야 하며, 아직 미달인 필수 항목은 공통 N·N번입니다(없으면 없음). 핸드오프하려면 권장 점수도 90점 이상이어야 합니다. 남은 대답과 확인은 아래와 같습니다. 이어서 진행할까요?

- 대답이나 외부 확인을 받지 못해 80점 전에 더 진행할 수 없으면 현재 점수, 남은 질문, 물어볼 담당자를 알리고 답을 기다린다. 이 경우 완료라고 말하지 않는다.
- 80점을 넘기려고 세부 기준을 줄이거나 지키지 않은 기준을 지킴으로 적지 않는다("채점 방법").

#### 리팩토링

사용자가 시작하자고 하면 아래 순서로 한다.

1. 커밋하지 않은 변경이 있으면 사용자에게 알리고 먼저 커밋해 되돌아갈 지점을 만든다(8번). git이 없으면 먼저 설정한다.
2. `ax-refactor/YYYYMMDD-HHmmss` 브랜치를 만들어 그 브랜치에서만 작업한다. main 등 기본 브랜치에서 직접 고치지 않는다.
3. 리포트의 미달 세부 기준을 "규격화와 리팩토링" 순서대로 고친다. 테스트가 없으면 "테스트가 없는 프로젝트"부터 한다.
4. 리팩토링 전에 만든 테스트를 다시 실행해 전후 결과를 비교하고, 이상이 있으면 다음으로 넘어가기 전에 고친다.
5. 다시 검사해 새 리포트를 만들고, 이전 리포트와 비교해 알린다(예: `62점 → 81점, +19점`). 항목별 변화도 리포트에 적는다.
6. 핸드오프 기준을 채우지 못했으면 3번으로 돌아가 채울 때까지 반복한다. 마이그레이션 요청으로 시작했으면 80점을 넘긴 뒤 이어서 진행할지 먼저 묻는다.
7. 핸드오프 기준을 채우면 핵심 흐름을 사용자가 직접 눌러 확인하게 하고, 결과를 리포트의 "동작 검증"에 적는다.

- 시작 동의는 다른 확인을 대신하지 않는다. 큰 변경의 계획 확인("규격화와 리팩토링"), 의존성 업그레이드(5번), 되돌리기 어려운 작업(7번)은 따로 확인을 받는다.
- 사용자 확인이나 외부 조치가 있어야 고칠 수 있는 기준(키 재발급, 승인된 외부 AI 확인 등)이 남으면, 무엇이 왜 막혔는지 사용자에게 알리고 답을 기다린다. 이 기준이 필수 항목에 있으면 해결되기 전에는 핸드오프할 수 없다.
- 기본 브랜치로 합치는 것은 사용자 확인을 받은 뒤에 한다.

#### 핸드오프

핸드오프 기준을 채우고 동작 검증까지 마치면 아래 문장으로 안내한다. 기준을 채우지 못했으면 이 문장을 쓰지 않는다. 메일은 사용자가 직접 보내고, 에이전트가 보내지 않는다.

> 필수 항목을 모두 100점으로 채웠고 권장 점수는 NN점입니다. AXTF에 핸드오프할 준비가 되었습니다. 리포트(`reports/...-ax-검사-리포트.md`)는 axtf-support@daewoong.co.kr로 전달해주세요!

### 개발 순서: 스펙 → 행동 → 테스트 → 코드

기능 추가와 버그 수정은 SDD(Spec-Driven), BDD(Behavior-Driven), TDD(Test-Driven) 순서로 한다. 테스트 코드는 선택이 아니다. 테스트를 만들고 실행하지 않은 기능은 완료가 아니다.

| 단계   | 목표                                         | 답할 질문                                          | 산출물                                                                             |
| ------ | -------------------------------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 1. SDD | 무엇을 만들지 코드보다 먼저 글로 합의한다    | 누구를 위해 무엇을 만들고, 어떤 조건이면 완료인가? | `docs/specs/<기능>.md`의 목적·권한·입출력·규칙·수용 기준(AC)                       |
| 2. BDD | 수용 기준을 사용자가 보는 행동 예시로 바꾼다 | 사용자가 무엇을 하면 어떤 결과가 보여야 하는가?    | 같은 파일의 시나리오(S, 전제-행동-결과)와 그 시나리오를 그대로 옮긴 E2E·API 테스트 |
| 3. TDD | 코드 단위가 맞게 동작함을 보장한다           | 이 함수가 이 입력에 무엇을 돌려줘야 하는가?        | 실패하는 단위 테스트 → 통과하는 최소 코드 → 리팩토링                               |

스펙 파일은 아래 형식으로 쓴다.

```txt
# <기능 이름>
## 목적
## 사용자와 권한        # 10번 권한 표 기준
## 입력과 출력
## 규칙
## 수용 기준
- AC-01: ...
## 시나리오
### S-01 (AC-01) <제목>
- 전제: ...
- 행동: ...
- 결과: ...
```

- SDD: 사용자의 요청을 받아 스펙 초안을 에이전트가 쓴다. 수용 기준과 시나리오만 쉬운 말로 사용자에게 확인받는다. 사용자는 화면에서 무엇이 보여야 하는지만 답하면 된다.
- BDD: 수용 기준마다 시나리오를 하나 이상 만든다. 정상 흐름과 함께 잘못된 입력, 권한 없음(15번), 데이터 없음 시나리오를 넣는다. 테스트 이름에 시나리오 ID(S-01)를 넣어 스펙과 테스트를 연결한다.
- TDD: 테스트를 먼저 쓰고 실행해 실패하는 것을 확인한 뒤 코드를 쓴다. 통과하면 리팩토링하고 다시 실행한다. 처음부터 통과하는 테스트는 아무것도 검증하지 않을 수 있으므로 테스트를 다시 본다.
- 버그 수정은 버그를 재현하는 테스트를 먼저 만들어 실패를 확인한 뒤 고친다. 스펙에 빠진 규칙이면 스펙에도 추가한다.
- 테스트를 통과시키려고 테스트를 지우거나, 건너뛰게 하거나(`skip`, `xfail`, `@Disabled`, `.only`), 기대값을 바꾸지 않는다. 기대값을 바꿔야 하면 스펙을 고치고 사용자 확인을 받는다.
- 동작을 바꾸지 않는 리팩토링은 새 스펙 없이 기존 테스트로 확인한다. 테스트가 없는 프로젝트는 아래 "테스트가 없는 프로젝트"를 먼저 따른다.
- 테스트 도구와 위치는 TS-7, PY-6, JV-6을 따른다.

### 규격화와 리팩토링

목표: 같은 스택의 앱은 같은 도구·폴더 구조·아키텍처·코드 스타일을 갖는다. 그래야 다른 사람이나 다른 에이전트가 넘겨받아도 바로 고칠 수 있다.

- 기존 코드를 처음 열면 "AX 검사와 핸드오프"에 따라 검사하고, 리포트의 미달 세부 기준을 `README.md`의 "표준 적용 현황"에 목록으로 남긴다. 고칠 때마다 목록을 갱신하고, 새 대화에서는 이 목록부터 읽는다.
- 고치는 순서:
  1. 현재 동작을 확인하는 테스트를 먼저 만든다. 테스트가 없으면 아래 "테스트가 없는 프로젝트" 순서를 따른다.
  2. 보안 규칙(1~17번) 위반을 고친다.
  3. 버전 고정과 도구(lint·포맷·타입 검사·테스트 명령)를 스택 규칙대로 맞춘다.
  4. 아키텍처(계층 분리, 프론트엔드·백엔드 분리)를 맞춘다.
  5. 폴더 구조와 코드 스타일을 맞춘다. 포맷은 도구로 자동 적용한다.
- 리팩토링은 동작을 바꾸지 않는다. 기능 변경과 리팩토링을 한 커밋에 섞지 않는다.
- 리팩토링 커밋은 `refactor` 타입을 쓰고, 기능 변경과 버그 수정은 `feat`, `fix`로 나눠 커밋한다(8번).
- 한 번에 한 단계씩 고치고, 단계마다 lint·테스트를 실행해 통과하면 커밋한다. 실패하면 그 단계를 되돌리거나 고친 뒤 다음으로 넘어간다.
- 사용자가 다른 기능을 요청한 대화에서는 그 작업이 건드리는 파일만 표준에 맞춘다. 전체 리팩토링은 따로 제안한다.
- 스택 전환, DB 전환, 프론트엔드·백엔드 분리처럼 큰 변경은 계획을 쉬운 말로 설명하고 확인을 받은 뒤 시작한다. 이런 변경은 Strangler Fig 방식으로 한다: 새 구조를 옆에 만들고 기능을 하나씩 옮겨 연결을 바꾼 뒤, 옮긴 기능의 예전 코드를 지운다. 한 번에 전부 다시 쓰지 않는다.
- 리팩토링 기법과 아키텍처 패턴 이름은 마틴 파울러의 『리팩터링』 2판과 『엔터프라이즈 애플리케이션 아키텍처 패턴』(PoEAA)을 따른다. 이 파일에 이름이 나오면 그 정의대로 적용한다.
- 한 단계에는 기법 하나만 적용한다(예: 함수 추출하기 → 테스트 → 커밋 → 함수 옮기기 → 테스트 → 커밋).
- 기능을 넣기 어려운 구조면 먼저 구조를 고쳐 커밋한 뒤 기능을 넣는다.
- 같은 코드가 세 번째 나오면 공통 함수로 뽑는다. 아직 쓰지 않는 확장 지점(추상 클래스, 설정 옵션, 플러그인 구조)은 미리 만들지 않는다.

### 테스트가 없는 프로젝트

바이브코딩으로 만든 앱은 테스트가 없는 경우가 많다. 테스트 없이 구조를 바꾸면 무엇이 깨졌는지 알 수 없으므로, 리팩토링 전에 아래 순서로 안전망을 만든다.

1. 테스트 도구와 실행 명령을 준비한다(TS-1, PY-1, JV-1).
2. 스모크 테스트: 앱이 실행되는지, 모든 화면과 API가 오류 없이 응답하는지 확인한다.
3. 특성 테스트(characterization test): 지금 코드가 내놓는 결과를 그대로 기록해 기대값으로 삼는다. 결과가 맞는지 판단하는 테스트가 아니라, 리팩토링 뒤에도 같은 결과가 나오는지 비교하는 테스트다. 계산·변환·파일 처리 함수와 API 응답부터 만든다.
4. 핵심 흐름 테스트: 사용자에게 "이 앱으로 가장 자주 하는 일 3가지"를 화면 기준으로 묻고(어느 화면에서 무엇을 누르면 무엇이 나오는지), 그 흐름을 E2E 테스트로 만든다.
5. 권한 테스트(15번).

- 1~4단계를 마치기 전에는 구조를 바꾸는 리팩토링(규격화 4~5단계)을 시작하지 않는다. 포맷 자동 적용, 코드에 적힌 비밀정보 제거(1번)처럼 동작을 바꾸지 않거나 급한 수정은 먼저 해도 된다.
- 테스트 데이터는 실제 자료가 아닌 가짜 데이터로 만든다(3번). 외부 API·AI 호출은 가짜 응답(mock)으로 바꿔 테스트 중에 요금이 나가거나 데이터가 전송되지 않게 한다(2번).
- 특성 테스트를 만들다 버그로 보이는 결과를 발견하면 그 자리에서 고치지 않는다. "표준 적용 현황"에 기록하고 사용자에게 알린 뒤, 리팩토링과 별도 커밋으로 고친다.
- 테스트를 만들 수 없는 부분(테스트용 외부 시스템이 없는 경우 등)은 "표준 적용 현황"에 "테스트 없음"으로 표시하고, 그 부분의 구조 변경은 최소로 한다.
- 이후 새 기능과 버그 수정은 "개발 순서"를 따른다.

### 작업을 마칠 때

- 해당 스택의 lint·포맷·타입 검사·테스트 명령(TS-1, PY-1, JV-1)을 실행하고 오류를 모두 해결한다. 실패하면 완료라고 말하지 않는다. 테스트 결과(통과·실패·건너뜀 개수)와 이번에 추가한 시나리오 ID를 함께 알린다.
- 이번 변경이 공통 규칙과 해당 스택 규칙에 어긋나지 않는지 스스로 점검하고, 결과를 쉬운 말로 짧게 알린다. 리팩토링을 했으면 "표준 적용 현황"을 갱신한다.
- 사용자가 "규칙 파일 기준으로 점검해줘"라고 하면 공통 1~17번과 해당 스택 규칙을 하나씩 확인해 점수를 매기고 리포트를 만든다("AX 검사와 핸드오프").
- 코드를 수정한 뒤에는 앱이 예전처럼 동작하는지 사용자가 직접 눌러 확인하도록 안내한다. 사용자가 해결하기 어려워하면 소속 부서의 현업 배치 개발자에게 도움을 요청하도록 안내한다.

## 공통 규칙

모든 웹앱에 항상 적용하는 보안·운영 규칙(1~17번)이다.

### 1. 비밀정보를 코드에 쓰지 않는다

이유: 코드가 공유되면 키도 함께 유출되어 요금이 청구되거나 회사 시스템에 무단으로 접근할 수 있다. AI는 빨리 동작시키려고 키를 코드에 바로 쓰는 경향이 있다.

- API 키, 토큰, 비밀번호, DB 접속 정보를 코드·설정 파일·주석에 직접 쓰지 않는다. 환경 변수에서 읽는다.
- `.env`는 `.gitignore`에 추가한다. 필요한 항목은 값을 비운 `.env.example`에 적는다.
- 코드에 적힌 비밀정보를 발견하면 파일 경로와 줄 번호를 알린다. 이미 공유·커밋된 적 있는 키라면 코드 수정만으로는 해결되지 않는다고 알리고, 발급한 서비스에서 키를 재발급하고 기존 키를 폐기하도록 안내한다.
- 비밀정보 값을 화면·답변에 출력하지 않는다(로그는 12번). 확인할 때는 변수 이름과 설정 여부만 말한다.

### 2. 회사 데이터를 승인되지 않은 외부 AI로 보내지 않는다

이유: 외부 AI로 보낸 자료는 회수할 수 없고, 서비스의 약관과 설정에 따라 저장되거나 학습에 쓰일 수 있다.

- 외부 API, AI 서비스, 분석 도구, MCP 서버를 새로 연결하기 전에 보낼 데이터 항목을 사용자에게 설명하고 확인을 받는다. 회사 데이터나 개인정보를 외부 AI로 보내는 기능은 승인된 서비스와 허용 데이터 범위까지 확인받기 전에는 구현하지 않는다. 이미 연결돼 있으면 그 사실을 알린다.
- 실제 파일을 읽을 때는 열 이름 등 구조만 먼저 확인한다. 실제 값이나 본문을 읽어야 하면 먼저 사용자에게 묻는다. 외부 AI와 연결된 도구로 파일을 읽는 것도 외부 전송으로 보고 이 규칙을 적용한다.
- 전송이 허용된 경우에도 필요한 항목만 보낸다. 불필요한 개인정보와 회사 기밀은 사내 또는 로컬 환경에서 먼저 지우거나 가린다. 가리기 위해 원문을 외부 AI에 먼저 보내지 않는다. 가린 뒤에도 사람·거래처를 알아볼 수 있거나 허용 범위 밖의 기밀이 남아 있으면 보내지 않는다. 마스킹했다는 이유로 승인되지 않은 외부 AI를 사용하지 않는다.
- 점검을 요청받으면 앱이 호출하는 외부 서비스를 모두 찾아 `서비스 | 보내는 데이터 | 개인정보 포함 여부 | 회사 데이터 포함 여부` 표로 정리한다.

### 3. 실제 데이터 파일은 권한이 있는 사용자만 접근하게 한다

이유: 앱 화면을 보호해도 엑셀·PDF 같은 원본 파일이 노출되면 회사 자료가 그대로 유출된다.

- 엑셀·PDF·CSV·JSON 파일을 앱 데이터로 써도 된다. 실제 자료는 `data/` 폴더에 모으고, 소스 코드 안에 배열·문자열로 붙여 넣지 않는다. 이미 코드 안에 있으면 파일로 분리한다.
- 실제 자료가 있는 앱과 파일은 회사가 허용한 환경(내 PC, 사내 서버·앱허브, 접근이 제한된 저장 공간)에서만 실행·보관한다.
- 파일 주소로 직접 열거나 내려받는 경로에도 10번의 권한 확인을 적용한다. 앱 로그인만으로는 막히지 않는다.
- 앱 폴더를 다른 사람에게 넘기기 전에 함께 넘어가는 자료와 그 자료를 볼 수 있게 되는 사람을 설명하고 확인을 받는다. 외부 저장소·배포 서비스에 올릴 때는 6번을 따른다.
- 회사 데이터·개인정보가 담긴 파일은 저장소에서 제외하고 서버의 비공개 공간으로 따로 전달한다. 파일 경로를 `.gitignore`에 넣되, 이미 Git이 추적 중인 파일은 `.gitignore`만으로 제외되지 않으므로 추적 목록과 이전 커밋 기록도 확인한다. 배포 전에 앱이 그 파일을 읽을 수 있는지 확인하고, 저장 위치와 전달 방법을 `README.md`에 남긴다.
- 테스트·데모·화면 캡처에는 실제 자료 대신 같은 형식의 가짜 예시 파일을 만들어 쓴다.
- 동시 수정, 변경 이력, 사용자별 권한, 데이터 간 연결이 필요해지면 파일 대신 PostgreSQL로 옮기자고 제안한다. PDF 원본은 파일로 두고 관리 정보만 DB에 저장할 수 있다.

### 4. 개인정보를 다루면 사용자에게 알린다

이유: 개인정보는 법으로 더 엄격하게 관리해야 하며, 다룬다는 사실을 모를 때 가장 위험하다.

- 개인정보는 특정 사람을 알아볼 수 있는 정보다. 이름이 없어도 사번·고객 ID·연락처처럼 다른 자료와 맞춰 누구인지 알 수 있으면 개인정보다.
  - 직원: 이름, 사번, 연락처, 계좌번호, 인사평가, 급여
  - 고객: 의사·약사 등 고객 이름, 거래처 담당자 연락처, 고객 ID
  - 환자: 처방·진료·건강 정보
- 주민등록번호·여권번호·운전면허번호·외국인등록번호와 건강·진료 정보는 법에서 더 엄격하게 다룬다. 이 정보가 들어가는 기능은 사용자 확인 전에는 구현하지 않는다.
- 사람을 알아볼 수 없는 통계(부서별 인원, 월별 매출 합계 등)는 개인정보가 아니다.
- 개인정보를 다루는 기능을 만들거나 기존 코드에서 발견하면 어떤 항목을 어디에서 쓰는지 사용자에게 알린다.
- 개인정보는 화면·파일·API 응답에 꼭 필요한 항목만 남긴다(로그는 12번). 필요 없는 항목은 빼자고 제안한다.

### 5. 의존성 버전을 고정하고 취약점을 점검한다

이유: AI는 학습한 예전 버전을 쓰기 쉽고, 학습 이후 공개된 취약점을 알지 못한다. 버전을 고정하지 않거나 최신 버전을 자동으로 받으면 검증하지 않은 코드가 앱에 들어온다(공급망 공격). AI는 실제로 없는 패키지 이름을 지어내기도 하고, 공격자는 그런 이름이나 유명 패키지와 비슷한 이름으로 악성 패키지를 올려 둔다.

- 새 라이브러리는 현재 유지보수 중인 안정 버전을 쓴다. 같은 일을 하는 라이브러리가 이미 있으면 새로 추가하지 않는다.
- 새 라이브러리를 설치하기 전에 공식 저장소(npm, PyPI, Maven Central)에서 그 이름의 패키지가 실제로 있는지, 철자가 맞는지, 관리 주체·최근 배포일·다운로드 수를 확인하고 사용자에게 알린다. 이름이 비슷한 다른 패키지가 있거나, 최근에 처음 올라왔거나, 다운로드가 거의 없으면 설치하지 않고 사용자에게 묻는다.
- 직접 쓰는 의존성은 정확한 버전으로 적고, 잠금 파일을 만들어 커밋한다. 표기 방법·잠금 파일·점검 도구는 TS-1, PY-1, JV-1을 따른다.
- 사용자 확인 없이 의존성을 자동·일괄 업그레이드하지 않는다.
- 취약점은 최신 취약점 정보를 조회하는 도구로 판단한다. AI가 기억하는 정보만으로 안전하다고 판단하지 않는다.
- 점검 시점:
  - 새 대화에서 첫 코드 수정 전
  - 라이브러리를 추가하거나 버전을 바꾼 뒤
- 점검 범위: 의존성 파일과 잠금 파일을 함께 보고, 간접 의존성까지 포함한다.
- 심각도 High·Critical: 하던 작업보다 먼저 알린다. 라이브러리, 위험 내용, 수정된 버전, 올렸을 때 깨질 수 있는 부분을 쉬운 말로 설명하고, 확인을 받아 수정된 가장 가까운 버전으로 올린다.
- 심각도 Low·Medium: 목록으로만 알리고 하던 작업을 계속한다.
- 버전을 올린 뒤에는 점검 도구를 다시 실행해 취약점이 사라졌는지 확인한다.
- 쓸 수 있는 도구가 없으면 무엇을 설치할지 사용자에게 묻는다. 설치·실행할 수 없으면(인터넷 연결이 안 되는 경우 등) 의존성 목록과 버전을 정리해 알리고, 점검하지 못했다고 분명히 말한다. 추측으로 안전하다고 말하지 않는다.

### 6. 공개하기 전에 누가 보게 되는지 확인받는다

이유: 로그인 없이 공개한 앱은 링크만 알면 누구나 들어올 수 있고, 링크는 메신저·메일로 퍼지거나 검색에 노출된다. 회사 데이터나 개인정보가 있는 앱은 1~4번을 지켜도 화면을 통해 그대로 보인다.

- Vercel·Replit·Lovable 등 외부 배포 링크, ngrok 같은 공개 URL, GitHub 공개 저장소에 올리기 전에 공개 후 누구나 볼 수 있게 되는 데이터를 목록으로 알리고 확인을 받는다.
- 회사 데이터나 개인정보를 보여 주거나 바꿀 수 있는 앱은 사내 로그인(SSO)을 붙이거나 접근 대상을 제한한 뒤에만 공개한다.
- 회사 데이터와 개인정보가 없는 앱(공개 정보 안내 페이지, 계산기 등)은 로그인 없이 공개해도 된다.
- 로그인 없이 공개하는 앱이 외부 AI나 유료 API를 호출하면, 누구나 호출해 요금이 나갈 수 있다고 알리고 14번의 사용량 한도나 로그인을 붙인다.

### 7. 원본 데이터를 지우거나 덮어쓰기 전에 확인받는다

이유: AI가 오류를 고치려다 데이터를 지우거나 덮어쓰는 일이 있고, 비개발자는 그 명령이 위험한지 알아보기 어렵다. 구글 시트·엑셀은 원본이 하나뿐인 경우가 많아 한번 지워지면 되돌리기 어렵다.

- 구글 시트·엑셀·DB 같은 원본 데이터는 기본적으로 읽기만 한다. 앱이 데이터를 수정하거나 새로 저장해야 하면 먼저 사용자에게 알린다. 원본 파일을 수정할 때는 복사본을 만들어 작업한다.
- 삭제, 일괄 수정, 파일 덮어쓰기, `rm -rf`, `git push --force`, `DROP`·`TRUNCATE`, DB 마이그레이션으로 테이블·컬럼 삭제처럼 되돌리기 어려운 작업은 실행 전에 바뀌는 대상을 설명하고 확인을 받는다.

### 8. 변경 기록을 남긴다

이유: AI가 앱을 망가뜨려도 원래대로 되돌릴 수 있다. 비개발자에게는 이것이 유일한 백업인 경우가 많다.

- 프로젝트는 git으로 관리한다. git이 없으면 작업 시작 전에 설정을 제안한다.
- 큰 변경 전에는 커밋해 되돌아갈 지점을 만든다. 리팩토링은 작업 브랜치에서 한다("AX 검사와 핸드오프").
- 커밋 메시지와 커밋 단위는 "커밋 규칙"을 따른다.

### 9. 사용자 입력을 그대로 쓰지 않는다

이유: 입력창에 넣은 값이 그대로 실행되면 다른 사람의 데이터를 꺼내거나 지울 수 있다. AI 기능이 있는 앱은 입력 한 줄로 AI가 다른 사람의 자료를 보여 주기도 한다.

- 서버로 들어오는 모든 입력은 스키마로 형식·길이·범위를 검증한다(PY-3, JV-3).
- DB 쿼리에 입력값을 문자열로 이어 붙이지 않는다. 파라미터 바인딩이나 ORM을 쓴다.
- 사용자가 올리거나 고른 파일명으로 파일을 저장하거나 열 때는 정해진 폴더 밖으로 나가지 못하게 경로를 검사한다.
- 사용자 입력을 HTML에 그대로 넣지 않는다(TS-5). 화면을 꾸미려고 HTML을 쓸 때도 사용자 입력을 섞지 않는다.
- 사용자 입력을 AI에게 넘기는 기능은 AI가 볼 수 있는 자료를 그 사용자의 권한 범위(10번)로 제한하고, AI의 답만으로 데이터를 삭제·수정하지 않는다.

### 10. 데이터 조회 권한은 서버에서 요청마다 확인한다

이유: 화면에서 버튼만 숨기면 주소나 요청을 바꿔 다른 사람의 자료를 볼 수 있다. 오류 화면에 자세한 내용이 나오면 코드와 설정이 그대로 드러난다.

- 데이터를 연결하기 전에 사용자에게 물어 권한 표를 만든다: `데이터 | 볼 수 있는 사용자(역할·소속) | 범위(전체 / 소속 팀 / 본인)`. 확정한 표는 `README.md`에 남긴다.
- 여러 사람이 쓰는 앱은 "이 사용자가 이 데이터를 볼 수 있는지"를 요청마다 백엔드에서 확인한다. 화면에서 숨기는 것은 권한 확인이 아니다.
- 화면 조회, 검색, 다운로드(파일 주소로 직접 여는 경로 포함), API 등 모든 조회 경로에서 같은 권한 확인 함수를 사용한다. 권한 확인이 빠진 경로를 만들지 않는다. 위치는 PY-3, JV-3을 따른다.
- 배포할 때 디버그 모드를 끄고, 오류 화면·API 오류 응답에 코드·설정·비밀정보가 보이지 않게 한다.

### 11. 외부 스크립트를 고정하고 기본 보안 헤더를 적용한다

이유: 외부에서 불러오는 스크립트가 예고 없이 바뀌면 앱이 멈추거나 원치 않는 코드가 실행된다.

- 외부 스크립트는 패키지로 설치해 앱에서 직접 제공한다. CDN을 써야 하면 버전과 무결성 값(SRI)을 고정한다. 버전 없이 최신 버전을 자동으로 불러오지 않는다.
- 배포할 때 다음 보안 헤더를 적용한다(TS-6).
  - CSP: 허용한 곳의 스크립트·리소스만 실행하거나 불러오게 제한
  - `X-Content-Type-Options: nosniff`: 브라우저가 파일 형식을 추측하지 않게 제한
  - `Referrer-Policy`: 다른 사이트로 전달되는 주소 정보 제한

### 12. 원본 데이터와 민감정보를 로그에 남기지 않는다

이유: 오류를 찾으려고 남긴 로그에 CRM 원본이나 개인정보가 통째로 들어가면, 앱에서 데이터를 지켜도 로그로 새어 나간다.

- 업무 데이터 원문, 요청·응답 본문, 업로드 파일 내용, 개인정보, 비밀정보를 로그에 남기지 않는다. 필요한 경우 처리 결과, 건수, ID처럼 최소 정보만 남긴다.
- 로그는 스택의 표준 로깅 도구로만 남긴다. 화면 출력용 함수(`console.log`, `print`, `System.out.println`)로 남기지 않는다.
- 로그 레벨을 나눈다. 운영 환경은 INFO 이상만 남기고, DEBUG 로그와 상세 검증 기록은 개발 환경에서만 켠다.
- 로그 보관 기간을 정하고, 기간이 지나면 자동으로 지워지게 한다.

### 13. 상태와 설정을 표준 방식으로 관리한다

이유: 앱이 기억해야 할 내용을 메모리에만 두면 재시작할 때 사라지고, 서버를 여러 대로 늘리면 서로 다른 값을 보게 된다. 같은 방식으로 만들어야 앱허브에서 같은 방식으로 배포·운영할 수 있다.

- 재시작 뒤에도 남아야 하거나 여러 서버가 함께 써야 하는 상태는 메모리나 로컬 파일이 아니라 PostgreSQL에 저장한다.
- DB 테이블 구조는 마이그레이션 파일로만 바꾼다(PY-3, JV-3). 운영 DB를 손으로 고치거나 앱 시작 시 자동 생성하지 않는다.
- 실행 환경에 따라 달라지는 설정은 코드에 넣지 않고 환경 변수로 관리한다.
- 사내 표준 템플릿의 폴더 구조를 따르고, 프론트엔드·백엔드를 각각 컨테이너로 실행할 수 있게 만든다(`Dockerfile`은 각 폴더에 하나). FastAPI + HTML, Spring Boot + Thymeleaf 구조는 컨테이너 1개로 실행한다. 템플릿이 정해져 있지 않거나 찾을 수 없으면 스택 규칙의 구조를 쓰고, 임의로 바꾸지 않는다.
- 로컬에서 SQLite로 개발했다면 배포 전에 PostgreSQL로 전환해야 한다고 알린다. SQLite 전용 문법을 쓰지 않는다.

### 14. 입력과 사용량에 기본 한도를 둔다

이유: 너무 긴 입력, 큰 파일, 몰리는 요청 때문에 앱이 멈추거나 외부 서비스 요금이 크게 나올 수 있다.

- 입력 길이, 요청 크기(업로드 파일 포함), 사용자별 요청 횟수, 외부 호출 대기 시간(timeout)에 기본 한도를 정해 적용한다. 별도 설정이 없어도 한도가 적용되게 한다.
- 적용한 기본값은 설정 파일과 `README.md`에 남겨 사용자가 확인하고 조정할 수 있게 한다.
- 한도를 넘거나 대기 시간이 지나면 처리를 멈추고, 이유와 다시 시도할 방법을 쉬운 말로 화면에 보여 준다.

### 15. 권한과 핵심 기능을 확인하는 테스트를 남긴다

이유: 내 계정으로 화면이 잘 뜬다고 다른 사람의 자료까지 막힌 것은 아니다. 앱을 넘겨받는 사람도 같은 방법으로 확인할 수 있어야 한다.

- 권한 테스트와 핵심 기능 테스트를 함께 만든다. 도구는 TS-7, PY-6, JV-6을 따른다.
- 권한 테스트에는 10번 권한 표 기준으로 권한이 없는 계정(다른 소속 등)이 조회할 때 차단되는지 확인하는 경우를 넣는다.
- 테스트를 실행하고, 테스트 파일 위치·실행 방법·결과를 `README.md`에 남긴다.

### 16. 두 번 처리되면 안 되는 요청은 서버에서 한 번만 처리한다

이유: 버튼을 빠르게 두 번 누르거나, 네트워크가 끊겨 다시 보내거나, 뒤로 가기 뒤 다시 제출하면 같은 요청이 두 번 도착한다. 화면에서 버튼을 잠가도 이런 경우를 다 막지 못한다. 신청·결재·결제·발송이 두 번 처리되면 되돌리기 어렵다.

- 저장·제출 버튼은 누르는 즉시 잠그고 요청이 끝나면 푼다(디자인 시스템 인터랙션 가이드 7장). 시간으로 막는 debounce만으로 대신하지 않는다.
- 같은 요청이 두 번 와도 결과가 한 번과 같아야 하는 기능을 사용자와 정한다. 신청·결재·결제·외부 발송·포인트·재고처럼 횟수가 결과를 바꾸는 쓰기가 대상이다. 정한 목록은 `README.md`에 남긴다.
- 대상 기능은 서버에서 중복을 막는다. 아래 중 하나 이상을 쓴다.
  - 화면이 요청마다 고유 키(Idempotency-Key)를 만들어 보내고, 서버는 같은 키를 한 번만 처리하고 두 번째부터는 처음 결과를 돌려준다.
  - "사용자당 한 번" 같은 업무 규칙은 DB 유일 제약으로 막는다.
  - 상태가 바뀌는 처리는 바꾸기 전 상태를 조건으로 건다(예: `대기`일 때만 `승인`으로).
- 중복으로 막힌 요청에는 오류 대신 "이미 처리됐어요"처럼 결과를 알려 준다.
- 핵심 기능 테스트(15번)에 같은 요청을 두 번 보내도 한 번만 처리되는 경우를 넣는다.

### 17. 파일은 정해진 위치에만 저장한다

이유: 앱 소스 폴더 안에 저장한 파일은 내 PC에서는 되지만 사내 서버(앱허브)에서는 쓰기가 거부되어 `permission denied` 오류가 난다. 저장할 수 있는 위치라도 재시작·재배포 뒤에 남는지가 위치마다 달라서, 용도에 맞지 않는 곳에 두면 올린 파일이나 데이터가 사라지거나 깨진다.

- 사용자가 올린 파일과 앱이 만든 파일(문서·이미지 등)은 `/data` 폴더에 저장한다. 이 폴더의 파일은 앱을 재시작하거나 새로 배포해도 남는다.
- 경로를 코드에 직접 쓰지 않고 환경 변수 `UPLOAD_DIR`을 읽어서 쓴다. 앱허브에서는 `UPLOAD_DIR=/data`가 자동으로 들어가므로 따로 설정하지 않는다. 내 PC에서 개발할 때는 값이 없으므로 `./uploads`를 기본값으로 둔다.
- 저장할 것에 따라 위치를 나눈다.

  | 저장할 것 | 저장 위치 | 남는가 |
  | --- | --- | --- |
  | 업로드 파일, 생성한 문서·이미지 | `/data` (`UPLOAD_DIR`) | 재시작·재배포 뒤에도 남음 |
  | 잠깐 쓰고 버릴 임시 파일 | `/tmp` | 재시작하면 사라짐 |
  | 회원 정보, 게시글 같은 데이터 | DB(PostgreSQL) | 남음 |
  | 앱 소스 폴더 안(`./uploads`, `./data.db` 등) | 저장 불가 | 앱허브에서는 쓰기가 거부됨 |

- SQLite 같은 파일 DB를 `/data`에 두지 않는다. 파일이 깨질 수 있다. 데이터는 PostgreSQL을 신청해서 쓴다(13번).
- 로그를 파일에 계속 덧붙이지 않는다. 느려진다. 로그는 화면 출력(`print`, `console.log`)으로 남기면 자동으로 수집된다(12번).
- 앱 소스 폴더 안에 저장하지 않는다. 내 PC에서는 되지만 앱허브에서는 `permission denied` 오류가 난다.
- 사용자가 보낸 파일 이름을 그대로 경로에 붙이지 않는다. 정해진 폴더 밖으로 나가지 못하게 경로를 검사한다(9번).
- 저장 위치를 읽는 코드 예시는 스택 규칙(TS-9, PY-9, JV-9)을 따른다.
- 사용자가 AI 코딩 도구에 파일 저장을 요청하면 아래 문장을 쓰도록 안내한다.

  > 파일 업로드와 생성 파일은 환경 변수 `UPLOAD_DIR` 폴더에 저장해 줘. 값이 없으면 `./uploads`를 써. 앱 소스 폴더 안에는 파일을 저장하지 말고, 데이터는 SQLite 대신 PostgreSQL을 써. 임시 파일은 `/tmp`에 둬.

## 커밋 규칙

변경 기록(커밋)을 남길 때 적용한다. 지향점: 기록만 읽어도 무엇을 왜 바꿨는지 알 수 있고, 문제가 생기면 그 변경만 되돌릴 수 있다.

### 커밋 메시지

- 커밋 메시지는 Conventional Commits 1.0.0(https://www.conventionalcommits.org/ko/v1.0.0/) 형식 `<타입>(<범위>): <설명>`으로 쓴다. 범위는 생략할 수 있다. 타입은 영어로, 설명과 본문은 한국어로 쓴다. 설명에는 무엇을 왜 바꿨는지 한 줄로 적는다.
  - 타입: `feat`(기능 추가), `fix`(버그 수정), `refactor`(동작을 바꾸지 않는 구조 변경), `test`(테스트), `docs`(문서), `style`(포맷), `perf`(성능), `build`(빌드·의존성), `ci`(자동화), `chore`(그 외 관리 작업)
  - 예: `refactor(auth): 인증 라우트를 라우터 파일로 분리`, `fix(upload): 같은 이름 파일이 원본을 덮어쓰는 문제 수정`
  - 호환성을 깨는 변경은 타입 뒤에 `!`를 붙이고(`feat(api)!: ...`) 본문에 `BREAKING CHANGE:`로 영향을 적는다.

### 커밋 단위

- 한 커밋에는 한 가지 변경만 담는다. 기능 추가, 버그 수정, 리팩토링, 포맷 정리를 한 커밋에 섞지 않는다.
- 동작을 바꾸지 않는 구조 변경(`refactor`)과 동작을 바꾸는 변경(`feat`·`fix`)은 커밋을 나눈다. 리팩토링 전후 테스트 결과를 비교할 수 있어야 한다("규격화와 리팩토링").
- 테스트는 그 테스트가 확인하는 코드와 같은 커밋에 넣는다.

### 커밋하지 않는 것

- 비밀정보, `.env`, 회사 데이터·개인정보가 담긴 파일은 커밋하지 않는다(1번, 3번). 커밋하기 전에 변경된 파일 목록을 확인한다.
- 실수로 커밋했으면 기록을 고쳐 쓰기 전에 사용자에게 알린다. 이미 공유된 비밀정보는 재발급이 먼저다(1번).
- 공유된 기록을 덮어쓰지 않는다. 되돌릴 때는 되돌리는 커밋을 새로 만든다. `git push --force`는 7번을 따른다.

## TypeScript + React(Next.js) 규칙

프론트엔드 코드(`package.json`이 있는 폴더)에 적용한다. 지향점: 화면만 담당하는 얇은 프론트엔드. 타입으로 오류를 미리 막고, 서버 컴포넌트를 기본으로 해 브라우저로 보내는 코드를 줄인다.

### TS-1. 버전과 도구

- Node.js 26 LTS를 쓰고 `package.json`의 `engines.node`와 `.nvmrc`에 패치까지 적는다.
- 패키지 매니저는 pnpm만 쓴다. pnpm 버전은 `package.json`의 `packageManager`(예: `pnpm@10.x.y`)에 패치까지 적고, `pnpm-lock.yaml`을 커밋한다. `package-lock.json`·`yarn.lock`이 있으면 pnpm으로 옮기고 지운다(`pnpm import`).
- `.npmrc`에 `save-exact=true`를 둔다. 버전에 `^`, `~`, `*`, `latest`를 쓰지 않는다.
- 자동·일괄 업그레이드(`pnpm update`, `pnpm audit --fix`)는 사용자 확인 없이 실행하지 않는다. 취약점 점검은 `pnpm audit`로 한다.
- lint·포맷은 Biome 하나로 한다. 설정은 `biome.json`. ESLint·Prettier 설정이 있으면 Biome으로 옮기고 지운다.
- `package.json`의 scripts 이름을 맞춘다. 에이전트는 `pnpm <이름>`으로 실행한다.
  - `dev`, `build`, `start`
  - `lint`: `biome check .`
  - `format`: `biome check --write .`
  - `typecheck`: `tsc --noEmit`
  - `test`: 단위 테스트, `test:e2e`: E2E 테스트

### TS-2. TypeScript

- 모든 코드는 `.ts`·`.tsx`로 쓴다. `.js`·`.jsx`는 TypeScript로 옮긴다.
- `tsconfig.json`에 `"strict": true`와 `"noUncheckedIndexedAccess": true`를 켠다.
- `any`, `as any`, `@ts-ignore`를 쓰지 않는다. 타입을 모르면 `unknown`으로 받고 검사해서 좁힌다.
- 백엔드 응답, 폼 입력, URL 파라미터처럼 밖에서 들어오는 값은 zod 스키마로 검증하고, 타입은 스키마에서 만든다(`z.infer`).
- 타입은 쓰는 곳 가까이에 두고, 여러 기능이 함께 쓰는 타입만 `src/types/`에 둔다.

### TS-3. 프로젝트 구조

템플릿이 없으면 아래 구조를 쓴다.

```txt
src/
  app/                 # 라우트: page.tsx, layout.tsx, loading.tsx, error.tsx
  components/ui/       # 버튼·입력창 같은 공용 기본 요소
  features/<기능>/      # 기능별 컴포넌트·훅·스키마
  lib/api/             # 백엔드 API 호출(이곳에서만 fetch)
  lib/                 # 공용 유틸
  types/               # 여러 기능이 함께 쓰는 타입
public/                # 정적 파일(실제 업무 데이터는 두지 않는다, 3번)
```

- 파일 이름은 컴포넌트·훅을 포함해 모두 kebab-case로 쓴다(`user-table.tsx`, `use-user-list.ts`, `format-date.ts`). 코드 안의 컴포넌트 이름은 PascalCase(`UserTable`), 훅 이름은 `use`로 시작(`useUserList`)한다. Next.js가 정한 파일 이름(`page.tsx` 등)은 그대로 둔다.
- 파일 하나에 export하는 컴포넌트는 하나다. 컴포넌트가 200줄을 넘으면 나눈다.
- import는 `@/` 경로 별칭을 쓴다. `../../../`처럼 깊은 상대 경로를 쓰지 않는다.

### TS-4. 아키텍처

- 프론트엔드는 화면과 백엔드 API 호출만 맡는다. DB 접근, 업무 로직, 비밀키가 필요한 외부 호출은 백엔드(PY·JV 규칙)에 둔다. 기존 코드가 Next.js 안에서 DB에 접근하거나 업무 로직을 처리하면 백엔드로 옮긴다(규격화 4단계).
- Route Handler(`app/api/`)와 Server Action은 백엔드 호출을 중계하거나 로그인 쿠키를 넘길 때만 쓴다.
- 백엔드 호출은 `src/lib/api/`에서만 한다. 컴포넌트에서 `fetch`를 직접 부르지 않는다. 응답은 TS-2의 스키마로 검증한다.
- 권한 판단을 프론트엔드에서 하지 않는다(10번). 메뉴·버튼을 숨기는 것은 편의일 뿐이다.
- 브라우저에 노출되는 환경 변수(`NEXT_PUBLIC_`로 시작)에는 비밀값을 넣지 않는다.

### TS-5. React·Next.js 작성 방식

- Next.js App Router(`app/`)를 쓴다. `pages/` 라우터에 새 코드를 쓰지 않고, 기존 `pages/`는 `app/`으로 옮긴다.
- 함수형 컴포넌트와 hooks만 쓴다. 클래스 컴포넌트는 함수형으로 바꾼다.
- 서버 컴포넌트가 기본이다. `'use client'`는 상태, 이벤트 처리, 브라우저 API가 필요한 가장 작은 컴포넌트에만 붙인다.
- 첫 화면에 필요한 데이터는 서버 컴포넌트에서 가져온다. `useEffect` 안에서 데이터를 가져오지 않는다.
- 서버에서 받은 데이터를 전역 상태에 복사해 두지 않는다. 전역 상태 라이브러리는 필요한 이유를 설명할 수 있을 때만 추가한다.
- 스타일링 방식은 템플릿을 따르고, 한 프로젝트에 두 가지 이상 섞지 않는다.
- `dangerouslySetInnerHTML`, `innerHTML`을 쓰지 않는다(9번).
- 경로마다 `loading.tsx`와 `error.tsx`를 둔다. `error.tsx`에는 오류 상세 대신 다시 시도 방법을 보여 준다(10번·14번).

### TS-6. 보안 헤더와 설정

- 보안 헤더(11번)는 `next.config.ts`의 `headers()`에서 모든 경로에 적용한다.
- `next.config.ts`에 `poweredByHeader: false`를 둔다.
- 외부 스크립트는 npm 패키지로 설치해 쓴다. 외부 URL에서 스크립트를 불러오지 않는다.

### TS-7. 테스트

- 단위 테스트는 Vitest + React Testing Library로, 파일은 대상 옆에 `*.test.ts(x)`로 둔다.
- 로그인·권한·핵심 흐름(15번)은 Playwright E2E 테스트로 `e2e/`에 둔다.
- 테스트가 없는 프로젝트의 스모크 테스트는 Playwright로 모든 경로를 열어 오류 없이 뜨는지 확인한다. 특성 테스트는 Vitest 스냅샷(`toMatchSnapshot`)으로 만든다. 백엔드 호출은 MSW로 가짜 응답을 준다.
- 시나리오(S-n)는 Playwright 테스트로 만들고 이름에 시나리오 ID를 넣는다(`test('S-01 ...')`). TDD 단위 테스트는 Vitest로 만든다.

### TS-8. 아키텍처 패턴과 리팩토링

『리팩터링』 2판의 예제가 JavaScript라 기법을 그대로 적용한다. 다만 React는 클래스 대신 함수와 합성으로 구조를 만들기 때문에 아래처럼 바꿔 적용한다.

| 층        | 위치                                                 | 역할                    |
| --------- | ---------------------------------------------------- | ----------------------- |
| 표현      | `app/`, `components/`, `features/<기능>/`의 컴포넌트 | 그리기만 한다           |
| 화면 로직 | `features/<기능>/`의 훅·순수 함수                    | 상태 관리, 데이터 가공  |
| Gateway   | `lib/api/`(TS-4)                                     | 백엔드 호출과 응답 검증 |

- 단계 쪼개기: 컴포넌트에서 데이터 가공과 렌더링이 섞여 있으면 "데이터 준비 순수 함수 → 렌더링"으로 나눈다. 순수 함수는 단위 테스트한다.
- 클래스 추출하기 → 컴포넌트 추출·커스텀 훅 추출로 적용한다. 상속 관련 기법(메서드 올리기, 슈퍼클래스 추출하기 등)은 쓰지 않고, 재사용은 props와 `children` 합성으로 한다.
- 조건부 로직을 다형성으로 바꾸기 → 판별 유니언 타입(`type` 필드)과 객체 맵으로 적용하고, `switch`에는 `never`로 빠진 경우를 검사한다.
- 기본형을 객체로 바꾸기 → 사번·금액·기간은 zod 스키마와 브랜드 타입(`z.string().brand<'EmployeeId'>()`)으로 만든다.
- 반복문을 파이프라인으로 바꾸기 → `map`·`filter`로 바꾼다. `reduce`가 읽기 어려워지면 `for...of`를 쓴다.
- 레코드 캡슐화하기·가변 데이터 → props와 상태는 `readonly`로 두고 직접 고치지 않는다. 새 값을 만들어 바꾼다.
- 특이 케이스 추가하기 → 데이터 없음·로딩·오류 처리는 null 검사를 흩뿌리지 않고 빈 상태 컴포넌트와 `loading.tsx`·`error.tsx`(TS-5)로 모은다.

### TS-9. 파일 저장

- 업로드·생성 파일의 저장 위치는 `UPLOAD_DIR` 환경 변수로 읽고, 값이 없으면 `./uploads`를 쓴다(17번). 경로를 코드에 직접 쓰지 않는다.
- 사용자가 보낸 파일 이름은 그대로 경로에 붙이지 않고, 정해진 폴더 밖으로 나가지 못하게 검사한다(9번). 아래 예시는 위치를 읽는 부분만 보여 준다.

```ts
import path from "node:path";

const UPLOAD_DIR = process.env.UPLOAD_DIR ?? "./uploads";

const filePath = path.join(UPLOAD_DIR, fileName);
```

## Python + FastAPI 규칙

Python 백엔드 코드에 적용한다. 지향점: 요청을 받는 층, 업무 로직 층, DB 층을 나눈 단순한 계층 구조. 모든 입출력은 Pydantic 모델로 형식을 정한다.

### PY-1. 버전과 도구

- Python 3.15를 쓰고 `.python-version`에 패치까지 적는다. `pyproject.toml`에는 `requires-python = "==3.15.*"`를 둔다.
- 패키지 관리는 uv만 쓴다. 의존성은 `pyproject.toml`에 `==`로 고정하고 `uv.lock`을 커밋한다. `requirements.txt`·`Pipfile`·`poetry.lock`이 있으면 uv로 옮긴다.
- 자동·일괄 업그레이드(`uv lock --upgrade`, `pip install -U`)는 사용자 확인 없이 실행하지 않는다. 취약점 점검은 `pip-audit`로 한다.
- lint·포맷은 Ruff 하나로 한다. 설정은 `pyproject.toml`에 두고, lint 규칙은 `[tool.ruff.lint]`에 `select = ["E", "F", "W", "I", "B", "UP", "S", "SIM"]`을 기본으로 한다. pytest는 `assert`로 검증하므로 `[tool.ruff.lint.per-file-ignores]`에 `"tests/**" = ["S101"]`을 둔다. 이 예외는 규칙 파일이 정한 기본값이므로 사용자 확인 없이 둔다. Black·isort·flake8 설정이 있으면 Ruff로 옮기고 지운다.
- 타입 검사는 mypy로 한다. 설정은 `[tool.mypy]`에 `strict = true`, `plugins = ["pydantic.mypy"]`.
- 실행 명령을 맞춘다.
  - lint: `uv run ruff check .`
  - 포맷: `uv run ruff check --fix . && uv run ruff format .`
  - 타입 검사: `uv run mypy app`
  - 테스트: `uv run pytest`
  - 실행: `uv run uvicorn app.main:app`(`--reload`는 개발에서만)

### PY-2. 프로젝트 구조

템플릿이 없으면 아래 구조를 쓴다.

```txt
app/
  main.py              # FastAPI 앱 생성, 라우터·예외 처리 등록
  core/config.py       # 설정(pydantic-settings, 환경 변수)
  core/security.py     # 로그인 사용자 확인, 권한 확인 함수
  core/db.py           # DB 연결·세션
  api/routers/         # 기능별 엔드포인트 파일
  schemas/             # 요청·응답 Pydantic 모델
  services/            # 업무 로직
  repositories/        # DB 조회·저장
  clients/             # 외부 시스템·API 호출(Gateway)
  models/              # SQLAlchemy 테이블 모델
migrations/            # Alembic 마이그레이션
tests/
```

- 파일·함수·변수는 snake_case, 클래스는 PascalCase, 상수는 UPPER_SNAKE_CASE로 쓴다.
- 한 파일이 300줄을 넘으면 기능별로 나눈다.

### PY-3. 아키텍처

- 호출 방향은 router → service → repository 한 방향이다. router에서 DB를 직접 조회하지 않는다. service와 repository는 HTTP 요청·응답 객체를 모른다.
- 요청·응답은 Pydantic v2 모델로 정의하고 라우터에 `response_model`을 적는다. dict나 DB 모델 객체를 그대로 반환하지 않는다(필요 없는 필드와 개인정보가 함께 나간다, 4번).
- 입력 검증(9번)은 Pydantic 필드 제약(`Field(max_length=...)` 등)으로 한다.
- DB는 SQLAlchemy 2.x(`select()` 방식)로 다룬다. 테이블 구조 변경은 Alembic 마이그레이션으로만 한다. 운영에서 `create_all`로 테이블을 만들지 않는다.
- DB 세션과 로그인 사용자는 `Depends`로 주입한다. 권한 확인 함수는 `core/security.py` 한 곳에 두고 모든 라우터가 `Depends`로 쓴다(10번).
- 한 프로젝트 안에서 동기(`def`)와 비동기(`async def`) 방식을 섞지 않는다. 템플릿을 따르고, `async def` 안에서 동기 DB 드라이버나 블로킹 호출을 쓰지 않는다.
- 외부 HTTP 호출은 httpx로 하고 timeout을 반드시 지정한다(14번).

### PY-4. 코드 스타일

- 모든 함수의 인자와 반환값에 타입 힌트를 단다.
- 설정은 `core/config.py`의 `Settings(BaseSettings)` 한 곳에서 읽는다. 다른 곳에서 `os.environ`을 직접 읽지 않는다.
- 로그는 `logging`으로 남긴다. `print`를 쓰지 않는다(12번).
- 업무 오류는 직접 만든 예외 클래스로 던지고, `main.py`에 등록한 예외 처리기에서 HTTP 응답으로 바꾼다. 응답에 traceback을 넣지 않는다. `except Exception: pass`처럼 오류를 삼키지 않는다.

### PY-5. 운영 설정

- 운영에서는 `debug=False`로 실행하고, API 문서 화면(`/docs`, `/redoc`, `/openapi.json`)을 끄거나 로그인 뒤로 둔다.
- CORS는 프론트엔드 주소만 허용한다. `allow_origins=["*"]`를 쓰지 않는다.

### PY-6. 테스트와 전환

- 테스트는 pytest와 FastAPI `TestClient`로 `tests/`에 둔다. 권한 테스트(15번)는 `app.dependency_overrides`로 다른 사용자를 넣어 차단되는지 확인한다.
- 테스트가 없는 프로젝트는 엔드포인트마다 `TestClient`로 현재 응답을 기록하는 특성 테스트를 만든다(syrupy 스냅샷). 외부 HTTP 호출은 respx로 가짜 응답을 준다. 테스트 DB는 테스트마다 새로 만든다. Testcontainers로 운영과 같은 엔진(PostgreSQL)을 띄우고, Docker를 쓸 수 없으면 SQLite로 하되 그 사실을 `README.md`에 적는다.
- 시나리오(S-n)는 `tests/scenarios/`에 `TestClient` 테스트로 만들고 함수 이름에 시나리오 ID를 넣는다(`test_s01_...`). TDD 단위 테스트는 `tests/unit/`에 둔다.
- Streamlit·Gradio·Flask·Django 앱을 옮길 때는 계산·데이터 처리 함수를 `services/`로 옮겨 재사용하고, 화면은 TS 규칙으로 새로 만든다.

### PY-7. 아키텍처 패턴과 리팩토링

| 위치(PY-2)             | PoEAA 패턴                                                |
| ---------------------- | --------------------------------------------------------- |
| `api/routers/`         | Remote Facade: 얇은 진입점. 검증·호출·응답 변환만         |
| `schemas/`             | DTO                                                       |
| `services/`            | Service Layer: 업무 흐름과 트랜잭션 경계                  |
| `repositories/`        | Repository                                                |
| `models/` + SQLAlchemy | Data Mapper. `Session`이 Unit of Work와 Identity Map 역할 |
| `clients/`             | Gateway: 외부 시스템·API 호출을 감싼다                    |

- 업무 로직은 Transaction Script(요청 하나 = 서비스 함수 하나)로 시작한다. 같은 규칙이 여러 서비스에 반복되거나 상태 변화 규칙이 복잡해지면 그때 Domain Model(모델 객체의 메서드)로 옮긴다.
- DB 모델과 API 스키마를 한 클래스로 겸용하지 않는다(SQLModel `table=True` 모델을 응답으로 반환하지 않는다).
- 트랜잭션 커밋은 service에서 한다. repository는 commit하지 않는다. 요청 하나에 세션 하나를 쓴다.
- 목록 조회에서 연관 데이터를 쓰면 `selectinload`·`joinedload`를 명시해 N+1 조회를 막는다. 비동기 세션에서는 지연 로딩에 기대지 않는다.
- 여러 사람이 같은 데이터를 고칠 수 있으면 버전 컬럼(`version_id_col`)으로 Optimistic Lock을 건다.
- Python에 맞게 바꿔 적용한다.
  - 상속 관련 기법보다 함수, 합성, `Protocol`을 먼저 쓴다.
  - 기본형을 객체로 바꾸기·매개변수 객체 만들기 → `@dataclass(frozen=True)`나 Pydantic 모델로 만든다.
  - 조건부 로직을 다형성으로 바꾸기 → 딕셔너리 매핑이나 `match` 문을 먼저 검토한다.
  - 단계 쪼개기 → 파일 업로드 처리는 "읽기 → 검증 → 변환 → 저장" 함수로 나눈다.
  - 모듈 전역 변수에 상태를 두지 않는다(13번).

### PY-8. FastAPI + HTML 화면

FastAPI가 HTML 화면을 직접 제공하는 구조는 새 앱과 기존 앱 모두 쓸 수 있다. 기존 앱은 Next.js로 옮기지 않아도 되고, 새 앱은 "스택 판별"의 기준으로 정한다. 이 구조에는 TS 규칙(TS-1~TS-9)을 적용하지 않고 아래를 따른다.

- HTML은 `app/templates/`, JavaScript·CSS는 `app/static/`에 둔다. 실제 업무 데이터는 두지 않는다(3번). 한 파일이 300줄을 넘으면 기능별로 나눈다.
- 화면은 그리기와 API 호출만 맡는다. 업무 로직, DB 접근, 권한 판단은 백엔드에 둔다(10번).
- API 호출은 공통 함수 한 곳에서만 한다.
- 사용자 입력과 서버 응답은 `textContent`로 넣는다. HTML로 그려야 하면 DOMPurify로 정리한 뒤 넣는다(9번).
- 서버에서 HTML에 데이터를 채우면 Jinja2를 쓰고 자동 이스케이프를 끄지 않는다. 사용자 입력과 서버 응답에 `|safe`를 쓰지 않는다(9번).
- 외부 스크립트는 파일을 내려받아 `app/static/`에서 제공하고, 버전을 파일 이름이나 `README.md`에 남긴다. 외부 URL에서 불러오지 않는다(11번).
- 보안 헤더(11번)는 가장 바깥 미들웨어에서 오류·리다이렉트를 포함한 모든 응답에 적용한다.
- 로그인·권한·핵심 흐름(15번)은 Playwright E2E 테스트로 `tests/e2e/`에 둔다. 화면이 없는 시나리오는 PY-6을 따른다.

### PY-9. 파일 저장

- 업로드·생성 파일의 저장 위치는 `UPLOAD_DIR` 환경 변수로 읽고, 값이 없으면 `./uploads`를 쓴다(17번). 경로를 코드에 직접 쓰지 않는다.
- 사용자가 보낸 파일 이름은 그대로 경로에 붙이지 않고, 정해진 폴더 밖으로 나가지 못하게 검사한다(9번). 아래 예시는 위치를 읽는 부분만 보여 준다.

```python
import os

UPLOAD_DIR = os.environ.get("UPLOAD_DIR", "./uploads")
os.makedirs(UPLOAD_DIR, exist_ok=True)

path = os.path.join(UPLOAD_DIR, file.filename)
```

## Java·Kotlin + Spring Boot 규칙

Java·Kotlin 백엔드 코드와 Spring Boot가 제공하는 Thymeleaf 화면에 적용한다. 지향점: Spring Boot 표준 방식의 Controller → Service → Repository 계층. 생성자 주입과 DTO로 의존성과 노출 범위를 드러낸다.

### JV-1. 버전과 도구

- Java 25 LTS 또는 Kotlin 2.4를 쓴다. 한 모듈 안에서 두 언어를 섞지 않는다. 언어는 템플릿이나 기존 코드를 따르고, 둘 다 없으면 Java를 쓴다.
- JDK 배포처는 템플릿을 따르고, 없으면 Eclipse Temurin을 쓴다. Spring Boot는 지원 중인 최신 안정 버전을 spring.io에서 확인해 고정한다.
- 빌드는 Gradle Kotlin DSL(`build.gradle.kts`)과 Gradle Wrapper(`gradlew`, `gradle/wrapper/`)를 쓰고 커밋한다. 새 프로젝트에 Maven을 쓰지 않는다. 기존 Maven 프로젝트는 전환을 제안한다.
- Java 버전은 toolchain(`JavaLanguageVersion.of(25)`)으로, Kotlin 버전은 Kotlin 플러그인 버전으로 고정한다.
- Spring Boot가 관리하는 라이브러리는 Spring Boot 버전을 따르고 개별 버전을 덮어쓰지 않는다. 그 밖의 라이브러리는 정확한 버전으로 적는다. 버전 범위, `+`, `latest.release`를 쓰지 않는다.
- Gradle 의존성 잠금을 켜고 `gradle.lockfile`을 커밋한다. 취약점 점검은 `osv-scanner`로 한다.
- 포맷과 lint는 Spotless로 묶는다.
  - Java: google-java-format으로 포맷하고, Checkstyle `google_checks.xml`로 검사한다(Google Java Style).
  - Kotlin: ktlint로 포맷·검사한다. `.editorconfig`에 `ktlint_code_style = ktlint_official`을 둔다.
- 실행 명령을 맞춘다.
  - 포맷: `./gradlew spotlessApply`
  - lint·테스트 전체: `./gradlew check`
  - 실행: `./gradlew bootRun`

### JV-2. 프로젝트 구조

템플릿이 없으면 기능별 패키지 구조를 쓴다.

```txt
src/main/java(또는 kotlin)/<회사 패키지>/<앱>/
  Application
  common/config/       # 설정 클래스
  common/security/     # 인증·권한 확인
  common/error/        # 예외와 공통 오류 응답
  common/client/       # 외부 시스템 호출(Gateway)
  <기능>/
    <기능>Controller
    <기능>Service
    <기능>Repository
    <기능>Entity
    dto/               # 요청·응답 DTO
src/main/resources/
  application.yml, application-dev.yml, application-prod.yml
  db/migration/        # Flyway 마이그레이션
src/test/...           # main과 같은 패키지 구조
```

- 클래스는 PascalCase, 메서드·변수는 camelCase, 상수는 UPPER_SNAKE_CASE, 패키지는 소문자로 쓴다.

### JV-3. 아키텍처

- 호출 방향은 Controller → Service → Repository 한 방향이다. Controller는 입력 검증과 응답 변환만 하고, 업무 로직과 트랜잭션(`@Transactional`)은 Service에 둔다.
- Controller는 Entity를 그대로 반환하지 않고 DTO로 바꿔 반환한다(4번). DTO는 Java `record`, Kotlin `data class`로 만든다.
- 입력 검증(9번)은 Jakarta Bean Validation(`@Valid`, `@NotBlank`, `@Size` 등)으로 한다.
- DB는 Spring Data JPA로 다룬다. 직접 쿼리가 필요하면 `@Query`에 파라미터를 바인딩한다. 테이블 구조 변경은 Flyway 마이그레이션으로만 하고, 운영에서는 `spring.jpa.hibernate.ddl-auto=validate`로 둔다(`create`·`update` 금지).
- 의존성은 생성자 주입만 쓴다. 필드에 `@Autowired`를 붙이지 않는다.
- 인증·권한은 Spring Security로 처리한다. 권한 확인은 `common/security/`의 한 곳에 두고 `@PreAuthorize` 등으로 모든 조회 경로에 적용한다(10번).
- 오류는 `@RestControllerAdvice`에서 공통 응답으로 바꾼다. `server.error.include-stacktrace=never`, `server.error.include-message=never`로 둔다.
- 설정은 `application.yml`에 두고 비밀값은 `${DB_PASSWORD}`처럼 환경 변수로 읽는다. 설정 묶음은 `@ConfigurationProperties`로 받는다.
- Actuator를 쓰면 운영에서 `health` 외 엔드포인트를 노출하지 않는다.
- 외부 HTTP 호출은 `RestClient`로 하고 연결·응답 timeout을 지정한다(14번).

### JV-4. 코드 스타일

- Java: `Optional`은 반환값에만 쓰고 필드·인자에 쓰지 않는다. null을 반환하는 대신 `Optional`이나 예외를 쓴다.
- Kotlin: `val`을 기본으로 쓰고, `!!`를 쓰지 않는다. JPA Entity에는 `data class`를 쓰지 않는다. `kotlin-spring`·`kotlin-jpa` 플러그인을 적용한다.
- 로그는 SLF4J로 남긴다. `System.out.println`, `println`, `printStackTrace()`를 쓰지 않는다(12번).
- 예외를 잡아서 아무것도 하지 않고 넘기지 않는다.

### JV-5. 프로필

- `dev`와 `prod` 프로필을 나눈다. 운영 컨테이너는 `prod`로 실행하고, DEBUG 로그·H2 콘솔·개발용 데이터 생성은 `dev`에서만 켠다.

### JV-6. 테스트

- 테스트는 JUnit 5와 Spring Boot Test로 쓴다. Controller는 `@WebMvcTest`와 MockMvc로 테스트한다. Kotlin은 MockK를 써도 된다.
- 권한 테스트(15번)는 `spring-security-test`(`@WithMockUser` 등)로 권한 없는 사용자가 차단되는지 확인한다.
- 테스트가 없는 프로젝트는 `@SpringBootTest`와 MockMvc로 엔드포인트마다 현재 응답을 JSON 파일로 기록해 비교하는 특성 테스트를 만든다. 외부 HTTP 호출은 `MockRestServiceServer`로 가짜 응답을 준다. 테스트 DB는 Testcontainers로 운영과 같은 엔진(PostgreSQL)을 쓴다.
- 시나리오(S-n)는 MockMvc 테스트로 만들고 `@DisplayName("S-01 ...")`으로 시나리오 ID를 붙인다. TDD 단위 테스트는 JUnit 5로 Service·도메인 클래스 단위로 만든다.

### JV-7. 아키텍처 패턴과 리팩토링

Spring은 PoEAA 패턴을 거의 그대로 구현한다. 직접 만들지 않고 Spring 기능을 쓴다.

| 위치(JV-2)       | PoEAA 패턴                                         | Spring 구현                        |
| ---------------- | -------------------------------------------------- | ---------------------------------- |
| Controller       | Remote Facade                                      | `@RestController`                  |
| `dto/`           | DTO                                                | Java `record`, Kotlin `data class` |
| Service          | Service Layer                                      | `@Service` + `@Transactional`      |
| Repository       | Repository                                         | Spring Data `JpaRepository`        |
| Entity + JPA     | Data Mapper, Unit of Work, Identity Map, Lazy Load | Hibernate 영속성 컨텍스트          |
| `common/client/` | Gateway                                            | `RestClient`를 감싼 클래스         |

- 업무 로직은 Service의 Transaction Script로 시작한다. 규칙이 복잡해지면 Entity에 의도를 드러내는 메서드(`approve()`, `cancel()`)를 두는 Domain Model로 옮긴다. Entity의 setter는 공개하지 않는다(세터 제거하기).
- 연관관계는 지연 로딩(`fetch = FetchType.LAZY`)을 기본으로 하고, 목록 조회는 fetch join이나 `@EntityGraph`로 N+1 조회를 막는다. `spring.jpa.open-in-view=false`로 둔다.
- 여러 사람이 같은 데이터를 고칠 수 있으면 `@Version`으로 Optimistic Lock을 건다.
- 금액·기간 같은 값은 `@Embeddable` Value Object로 만든다.
- Entity 상속은 피한다. 꼭 필요하면 `SINGLE_TABLE` 전략을 쓴다.
- Java·Kotlin에 맞게 바꿔 적용한다.
  - 조건부 로직을 다형성으로 바꾸기 → Java는 `sealed interface` + `switch` 패턴 매칭, Kotlin은 `sealed class` + `when`으로 한다.
  - 상속보다 위임을 쓴다(서브클래스를 위임으로 바꾸기, 슈퍼클래스를 위임으로 바꾸기).
  - 기본형을 객체로 바꾸기 → Java는 `record`, Kotlin은 `@JvmInline value class`로 만든다.
  - 특이 케이스 추가하기 → Java는 `Optional`, Kotlin은 nullable 타입과 `?:`로 "없음"을 한곳에서 처리한다.

### JV-8. Spring Boot + Thymeleaf 화면

JV 규칙을 쓰는 앱이 화면을 Spring Boot에서 함께 제공하면 Thymeleaf를 쓴다(`spring-boot-starter-thymeleaf`). 프론트엔드와 백엔드를 나눈 앱은 화면에 TS 규칙을 적용한다. 이 구조에는 TS 규칙(TS-1~TS-9)을 적용하지 않고 아래를 따른다. 새로 JSP로 만들지 않는다.

- HTML은 `src/main/resources/templates/`, JavaScript·CSS는 `src/main/resources/static/`에 둔다. 실제 업무 데이터는 두지 않는다(3번). 한 파일이 300줄을 넘으면 기능별로 나눈다.
- 화면을 돌려주는 Controller는 `@Controller`로 쓰고, 입력 검증과 응답 변환만 한다. 업무 로직, DB 접근, 권한 판단은 Service 이하에 둔다(JV-3).
- 템플릿에는 Entity를 넘기지 않고 DTO만 넘긴다(JV-3).
- 값은 `th:text`로 출력한다. `th:utext`를 쓰지 않는다. JavaScript로 화면에 넣을 때는 `textContent`를 쓰고, HTML로 그려야 하면 DOMPurify로 정리한 뒤 넣는다(9번).
- 사용자 입력을 뷰 이름이나 Thymeleaf 표현식에 넣지 않는다(9번).
- 폼은 `th:action`으로 만들고 Spring Security의 CSRF 보호를 끄지 않는다.
- 화면 경로에도 API와 같은 권한 확인을 적용한다(10번). 템플릿에서 메뉴를 숨기는 것은 권한 확인이 아니다.
- 화면 오류는 `@ControllerAdvice`에서 공통 오류 화면으로 바꾼다. 오류 화면에 코드·설정·비밀정보를 보여 주지 않는다(10번).
- 외부 스크립트는 파일을 내려받아 `static/`에서 제공하고, 버전을 파일 이름이나 `README.md`에 남긴다. 외부 URL에서 불러오지 않는다(11번).
- 보안 헤더(11번)는 Spring Security 설정으로 오류·리다이렉트를 포함한 모든 응답에 적용한다.
- 로그인·권한·핵심 흐름(15번)은 Playwright E2E 테스트로 `src/test/`의 `e2e` 패키지에 둔다. 화면이 없는 시나리오는 JV-6을 따른다.

### JV-9. 파일 저장

- 업로드·생성 파일의 저장 위치는 `UPLOAD_DIR` 환경 변수로 읽고, 값이 없으면 `./uploads`를 쓴다(17번). 경로를 코드에 직접 쓰지 않는다.
- 사용자가 보낸 파일 이름은 그대로 경로에 붙이지 않고, 정해진 폴더 밖으로 나가지 못하게 검사한다(9번). 아래 예시는 위치를 읽는 부분만 보여 준다.

```kotlin
val uploadDir = System.getenv("UPLOAD_DIR") ?: "./uploads"

val target = java.nio.file.Path.of(uploadDir, fileName)
```
