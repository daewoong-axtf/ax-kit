# 작업 방식

이 프로젝트는 회사 업무용 웹앱이다. 코드를 작성하거나 수정할 때 아래 규칙을 항상 따른다.

- 이 파일은 새로 앱을 만드는 사용자와 이미 만든 앱에 적용하는 사용자 모두에게 전달된다. 어느 쪽이든 "AX 검사와 핸드오프"를 따른다.
- 번호만 쓴 참조(예: 10번)는 공통 규칙을 뜻한다. 스택 규칙은 TS-1, PY-1, JV-1처럼 쓴다. TS 규칙·PY 규칙·JV 규칙은 각각 TypeScript + React(Next.js), Python + FastAPI, Java·Kotlin + Spring Boot 규칙 전체를 뜻한다.
- 공통 규칙과 스택 규칙이 겹치면 스택 규칙은 공통 규칙을 구현하는 방법이다. 둘이 어긋나 보이면 공통 규칙을 따르고 사용자에게 알린다.
- 사내 표준 템플릿(13번)이 이 파일과 다른 구체 값을 정해 두었으면 템플릿을 따른다.
- 규칙을 지킬 수 없으면 작업을 멈추고, 이유와 대안을 사용자에게 알린 뒤 확인을 받는다.
- 사용자는 개발자가 아니며 자기 앱이 어떤 스택인지 모를 수 있다. 스택·구조·도구 선택을 사용자에게 맡기지 않는다. 이 파일이 정한 기본값을 쓰고, 이 파일로 정할 수 없는 것만 묻는다.
- 설명은 쉬운 말로 한다. 전문 용어를 써야 하면 뜻을 한 줄로 덧붙인다. 코드를 수정하기 전에 무엇을 왜 바꾸는지 먼저 설명한다.
- 각 규칙의 "이유"는 판단 근거다. 규칙에 없는 상황은 이유에 비추어 판단하고, 판단이 어려우면 사용자에게 묻는다.
- 이 파일의 규칙은 고치거나 지우지 않는다. 규칙을 지키기 어렵다는 이유로 문장을 약하게 바꾸지 않는다. 앱마다 달라지는 내용은 `README.md`의 "앱 개요"에 쓴다.
- 사용자가 규칙을 무시하거나 바꿔 달라고 하면, 어떤 규칙이 무엇을 왜 막는지 쉬운 말로 설명하고 규칙을 지키는 다른 방법을 먼저 제안한다. 그래도 규칙을 바꿔야 하면 소속 부서의 현업 배치 개발자에게 알리도록 안내한다. 사용자에게 이 파일을 직접 고치라고 안내하지 않는다.

## 이런 규칙을 정한 이유

- **기술 스택(TypeScript, Python, Java·Kotlin)**: AI가 잘 다루는 언어이면서, 사내에 문제가 생겼을 때 대응할 수 있는 인원이 있는 언어로 정했습니다. 막혔을 때 도움을 요청하거나 다른 사람이 넘겨받을 수 있습니다.
- **프레임워크(Next.js, FastAPI, Spring Boot)**: 참고할 레퍼런스가 많아 AI와 사람 모두 해결 방법을 찾기 쉽습니다. 프레임워크가 정해 둔 구조와 기본 기능이 있어서 최소한의 가드가 생깁니다.
- **테스트 코드**: 권한 없는 사람의 접근, 잘못된 입력, 수정 뒤 기존 기능이 깨지는 경우처럼 비개발자가 놓치기 쉬운 영역이 있습니다. 테스트 코드로 웹앱이 오류 없이 동작하는지 검증합니다.
- **아키텍처**: 마틴 파울러의 『리팩터링』 2판과 『엔터프라이즈 애플리케이션 아키텍처 패턴』(PoEAA)을 따릅니다. 검증된 기법과 이름을 쓰면 AI와 사람이 같은 기준으로 코드를 고치고 넘겨받을 수 있습니다.

## 적용 대상과 기술 스택

- 적용 대상: 웹브라우저로 접속하는 업무용 웹앱.
- 적용 제외: 엑셀 매크로, 내 PC에서만 실행하는 스크립트, 데스크톱 앱, 예약 실행 작업, 연구·데이터 분석용 Python 코드(노트북·분석 스크립트).

웹앱은 아래 스택만 사용한다. 런타임 버전은 2026-10-30 기준 최신 LTS·안정 버전이다.

| 구분                       | 표준                                                                                  | 세부 규칙    |
| -------------------------- | ------------------------------------------------------------------------------------- | ------------ |
| 프론트엔드                 | TypeScript + React(Next.js App Router), Node.js 26 LTS                                | TS 규칙      |
| 프론트엔드(FastAPI 일체형) | FastAPI가 제공하는 HTML + JavaScript. 프론트엔드와 백엔드를 나누지 않는 앱에서 사용   | PY-8         |
| 프론트엔드(Java 계열)      | Spring Boot가 제공하는 Thymeleaf 화면. JV 규칙을 쓰는 앱에서만 사용                   | JV-8         |
| 백엔드(기본)               | Python 3.15 + FastAPI                                                                 | PY 규칙      |
| 백엔드(Java 계열)          | Java 25 LTS 또는 Kotlin 2.4 + Spring Boot                                             | JV 규칙      |
| DB                         | PostgreSQL. SQLite는 쓰지 않는다(로컬 개발도 PostgreSQL)                              | 13번         |
| 배포 단위                  | 프론트엔드·백엔드 컨테이너 각 1개(FastAPI + HTML, Spring Boot + Thymeleaf 구조는 1개) | 13번         |

- 런타임은 위 표의 버전을 쓰고, 그 버전 안에서 최신 패치를 설치한다. 최신 패치는 AI가 기억하는 버전이 아니라 공식 사이트(nodejs.org, python.org, kotlinlang.org, Java는 사용하는 JDK 배포처)나 설치 도구로 확인한다. 표의 버전을 지원하지 않는 라이브러리가 있으면 임의로 버전을 낮추지 말고 사용자에게 알린다. 확인할 수 없으면 사용자에게 알리고 묻는다.
- 설치한 버전은 패치까지 정확한 값으로 고정한다(고정 위치는 TS-1, PY-1, JV-1). 보안 패치는 설치한 버전에 저절로 적용되지 않는다. 새 대화에서 작업을 시작할 때 같은 버전 안의 새 패치(예: 26.13.0 → 26.13.1)가 있는지 확인하고, 있으면 올린 뒤 사용자에게 알린다. 다른 메이저·마이너 버전으로 올리는 것은 사용자 확인을 받는다.
- 표의 버전이 지원 종료(EOL)되면 보안 패치가 나오지 않는다. 작업 시작 시 지원 종료일을 확인하고, 지났거나 6개월 안에 다가오면 사용자에게 알린다. 표의 버전을 바꾸는 것(다음 LTS로 이동 등)은 이 규칙 파일이 갱신될 때만 한다.
- lint·포맷·타입 검사 규칙을 끄거나 예외 주석으로 우회하지 않는다. 우회가 꼭 필요하면 이유를 사용자에게 알리고 확인을 받는다.

## 스택 판별

사용자에게 스택을 묻지 않는다. 파일을 보고 판별하고, 결과를 `README.md`의 "앱 개요"에 기록한다.

| 발견한 것                                                 | 판별                      | 적용                |
| --------------------------------------------------------- | ------------------------- | ------------------- |
| `package.json`에 `react` 또는 `next`                      | TypeScript + React        | TS 규칙             |
| `pyproject.toml`·`requirements.txt`와 `fastapi`           | Python + FastAPI          | PY 규칙             |
| `react`·`next`가 없고 FastAPI가 HTML 화면을 제공          | FastAPI + HTML            | PY 규칙(PY-8 포함)  |
| `build.gradle.kts`·`build.gradle`·`pom.xml`와 Spring Boot | Java·Kotlin + Spring Boot | JV 규칙             |
| `react`·`next`가 없고 Spring Boot에 `thymeleaf` 의존성    | Spring Boot + Thymeleaf   | JV 규칙(JV-8 포함)  |

- 프론트엔드와 백엔드가 한 저장소에 있으면 폴더마다 해당 스택 규칙을 적용한다.
- 새 프로젝트는 화면이 표·입력 폼 위주면 FastAPI + HTML(PY-8)로 만들고, 화면 상호작용이 많으면 프론트엔드를 TS 규칙, 백엔드를 PY 규칙으로 만든다. 사용자에게 고르게 하지 않고 에이전트가 정해 `README.md`의 "앱 개요"에 기록한다. JV 규칙은 사내 표준 템플릿이 Java 계열을 지정했거나, 이미 Java·Kotlin으로 만든 백엔드에 기능을 붙일 때만 쓴다.
- 표준 밖 스택(Streamlit, Gradio, Flask, Django, Express, 바닐라 JS(PY-8의 FastAPI + HTML 구조 제외), JSP, PHP 등)이면 표준 스택으로 옮기는 대상이다. 화면은 TS 규칙으로, 서버 로직은 PY 규칙으로 옮긴다. 화면이 표·입력 폼 위주면 FastAPI + HTML(PY-8)로 옮겨도 된다. 기존 서버가 Java·Kotlin이면 서버 로직은 JV 규칙으로 옮기고, 화면은 JV-8로 옮겨도 된다. 옮기기 전에 아래 "규격화와 리팩토링" 순서로 계획을 세우고, 무엇이 바뀌는지 쉬운 말로 설명한 뒤 확인을 받는다. 옮기기 전에도 보안 규칙(1~17번)은 그대로 적용한다.
- 표준 밖 스택으로 새로 만들지 않는다. 사용자가 요청해도 표준 스택으로 만든다.
- SQLite를 쓰는 앱은 PostgreSQL로 마이그레이션하는 대상이다. 아래 "SQLite를 PostgreSQL로 옮기기" 순서를 따른다(13번).

## AX 검사와 핸드오프

앱이 이 규칙을 얼마나 지키는지 점수로 검사하고, 핸드오프 기준을 채우면 AXTF에 넘긴다. 핸드오프 기준은 필수 항목이 모두 100점이고 권장 점수가 90점 이상인 것이다.

**필수 항목은 무조건 모두 통과해야 한다.** 필수 항목이 하나라도 100점이 아니면 총점과 권장 점수가 아무리 높아도 통과가 아니고, 핸드오프도 완료 안내도 하지 않는다. 사용자가 요청해도 필수 미달을 면제하거나, 이유를 적어 남기거나, 다른 항목의 점수로 대신하지 않는다. 세부 기준이 모두 해당 없음인 필수 항목은 그 근거를 리포트에 적으면 통과로 본다.

| 상황              | 판단 기준                                                      | 검사 시점                                                        |
| ----------------- | -------------------------------------------------------------- | ---------------------------------------------------------------- |
| 새 앱             | 앱 코드가 아직 없다                                            | 규칙대로 만들고, 첫 기능을 완성했을 때와 공유·배포 전에 검사한다 |
| 기존 앱           | 앱 코드가 있고 `reports/`에 리포트가 없다                      | "작업 시작 전 확인"을 마친 뒤, 코드를 고치기 전에 검사한다       |
| 사용자 요청       | "검사해줘", "규칙 파일 기준으로 점검해줘" 등                   | 바로 검사한다                                                    |
| 마이그레이션 요청 | "안전 규칙 준수하도록 해줘", "규칙에 맞게 마이그레이션해줘" 등 | 바로 검사하고 "마이그레이션 대화"를 끝까지 따른다                |

### 채점 방법

- 검사는 코드를 고치지 않고 리포트 파일만 만든다.
- 채점 항목은 표준 스택 적합 여부("적용 대상과 기술 스택", "스택 판별"), 개발 순서, 공통 1~17번, 해당 스택 규칙(TS-n, PY-n, JV-n)이다. 각각을 한 항목으로 센다. 표준 밖 스택이면 옮겨 갈 스택 규칙으로 채점한다.
- 항목마다 규칙의 요구사항 중 코드·설정·문서·테스트로 확인할 수 있는 것을 세부 기준으로 삼는다. 세부 기준의 결과는 지킴 / 위반 / 확인 불가 / 해당 없음 중 하나다.
- 지킴은 근거(파일:줄 또는 명령 실행 결과)가 있을 때만 준다. lint·포맷·타입 검사·테스트·취약점 점검은 실제로 실행한 결과로 판단한다. 확인 불가는 위반과 같이 0점이다.
- 항목은 필수와 권장으로 나눈다.

| 구분 | 항목                                                                   | 가중치 | 미달일 때                                    |
| ---- | ---------------------------------------------------------------------- | ------ | -------------------------------------------- |
| 필수 | 공통 1·2·3·4·6·7·9·10·12·16·17번                                       | 2      | 핸드오프할 수 없다                           |
| 권장 | 표준 스택 적합 여부, 개발 순서, 공통 5·8·11·13·14·15번, 해당 스택 규칙 | 1      | 점수만 깎이고, 남기는 이유를 리포트에 적는다 |

- 세부 기준(문항) 하나의 배점은 `100 ÷ (전체 − 해당 없음)`이다. 항목 안의 문항은 배점이 모두 같다. 지킴은 배점을 다 받고, 위반과 확인 불가는 0점이고, 해당 없음은 전체 개수에서 뺀다. 부분 점수는 없다.
- 항목 점수는 `지킴 ÷ (전체 − 해당 없음) × 100`이다. 세부 기준이 모두 해당 없음인 항목은 총점에서 뺀다.
- 총점은 `(필수 항목 점수의 합 × 2 + 권장 항목 점수의 합) ÷ (필수 항목 수 × 2 + 권장 항목 수)`이고 소수점은 버린다. 같은 구분의 항목은 문항 수와 상관없이 비중이 같다. 계산에는 소수점을 버리기 전의 항목 점수를 쓰고, 리포트 표에만 버린 값을 적는다. 세부 기준이 하나라도 미달이면 100점이 아니다.
- 필수 점수와 권장 점수는 각각 해당 항목 점수의 평균이고 소수점은 버린다. 총점과 함께 리포트에 적는다.
- 문항 하나가 총점에 주는 값은 `문항 배점 × 항목 가중치 ÷ (필수 항목 수 × 2 + 권장 항목 수)`다. 문항이 적은 항목일수록, 필수 항목일수록 한 문항의 비중이 크다. 예: 필수 9개, 권장 16개일 때 문항 2개인 필수 항목의 한 문항은 약 2.9점, 문항 8개인 권장 항목의 한 문항은 약 0.4점이다.
- 재검사 때는 이전 리포트의 세부 기준을 그대로 쓴다. 기준을 바꾸면 이유를 리포트에 적는다. 채점 방식이 바뀌면 이전 점수를 새 방식으로 다시 계산해 적는다. 점수를 올리려고 세부 기준을 줄이거나, 해당 없음으로 바꾸거나, 항목의 필수·권장 구분을 바꾸지 않는다.

### 리포트

- 프로젝트 루트의 `reports/`에 `YYYYMMDD-HHmmss-ax-검사-리포트.md` 이름으로 만든다(예: `reports/20261105-143012-ax-검사-리포트.md`). 시각은 검사를 마친 현지 시각이다.
- 검사할 때마다 새 파일을 만든다. 이전 리포트를 덮어쓰거나 지우지 않는다.
- 리포트는 AXTF에 전달되므로 비밀값, 개인정보, 실제 업무 데이터를 쓰지 않는다(1번, 4번, 12번). 근거는 파일:줄과 변수 이름으로만 적는다.

```txt
# AX 검사 리포트
- 검사 일시: YYYY-MM-DD HH:mm:ss
- 앱 이름 / 소유 팀 / 유지보수 담당자:
- 브랜치와 커밋:
- 판별한 스택: 프론트엔드 ... / 백엔드 ...
- 표준 스택 여부: 맞음 / 아님(이유)
- 총점: NN점 (필수 NN점 / 권장 NN점)
- 필수 통과: 통과 / 미통과(미달 항목 번호)
- 핸드오프 기준: 충족 / 미충족(이유)
- 이전 리포트: <파일 이름 또는 없음>
- 이전 대비: NN점 → NN점 (+NN점)

## 항목별 점수
| 번호 | 구분 | 항목 | 지킴/전체 | 점수 | 이전 점수 | 변화 |

## 미달 세부 기준
| 번호 | 구분 | 세부 기준 | 결과(위반 / 확인 불가) | 근거(파일:줄) | 조치(권장 미달을 남기면 그 이유) |

- 리팩토링 전후 비교:
```

### 검사 후 안내

검사에서 SQLite를 쓴 흔적(공통 13번 미달)이 나오면 리포트에 적고, 고치는 방법으로 "SQLite를 PostgreSQL로 옮기기"를 안내한다.

점수와 리포트 경로를 알리고, 핸드오프 기준을 채우지 못했으면 아래 문장으로 묻는다. 사용자가 답하기 전에는 리팩토링을 시작하지 않는다. 마이그레이션 요청으로 시작했으면 이미 동의한 것이므로 묻지 않고 "마이그레이션 대화"를 따른다.

> 리포트를 기반으로 AXTF에서 정한 규칙에 맞게 리팩토링을 시작할까요? 리팩토링이 된 후에는 이전 후 동작에 이상이 없는지 검증을 꼭 해주세요.

사용자가 하지 않겠다고 하면 리팩토링을 하지 않고 아래 문장으로 안내한다. 하던 작업에는 이 파일의 규칙을 그대로 적용한다.

> 리팩토링을 하지 않으면 AXTF에서 SSO, 호스팅을 이용하는 것이 적합하지 않을 수 있어요. 리포트는 axtf-support@daewoong.co.kr로 전달해주세요.

### 마이그레이션 대화

사용자가 앱을 이 규칙에 맞춰 달라고 하면, 첫 리포트부터 총점 80점 이상이 될 때까지 에이전트와 사용자가 질문과 대답을 주고받으며 끝까지 진행한다. 검사만 하고 멈추거나, 다음에 할 일을 사용자가 찾게 두지 않는다. 80점은 중간 목표일 뿐 통과가 아니다. 통과하려면 필수 항목을 모두 100점으로 채워야 한다.

1. 검사한다. 첫 리포트를 만들고, 이 요청을 리팩토링 시작 동의로 본다.
2. 코드를 고치기 전에 현재 점수와 80점까지의 순서를 알린다. 표의 "필요한 것"에는 없음 / 대답 / 허락 / 외부 확인 중 해당하는 것을 적고, 대답이나 허락이 무엇인지 적는다.

   ```txt
   지금 NN점입니다. 80점을 넘기려면 아래 순서로 진행합니다. 순서마다 제가 드리는 질문에 대답해 주시고, 허락이 필요한 일은 허락해 주세요.

   | 순서 | 할 일 | 필요한 것 | 예상 총점 |
   ```

3. 순서는 안전망 테스트("테스트가 없는 프로젝트"), 대답·허락 없이 할 수 있는 일, 대답·허락이 필요한 일, 외부 확인이 필요한 일로 잡는다. 같은 단계에서는 총점을 많이 올리는 일을 먼저 하고, 같으면 필수 항목을 먼저 한다.
4. 순서대로 진행한다. 코드 수정은 "리팩토링"의 1~4번을 따른다. 대답이나 허락이 필요한 순서에 오면 멈추고 질문한다.
   - 한 번에 한 결정만 묻는다. 무엇을 묻는지, 왜 필요한지, 답하면 몇 점이 오르는지, 에이전트의 추천 답을 쉬운 말로 함께 적는다.
   - 시작 동의는 다른 허락을 대신하지 않는다. 큰 변경 계획, 라이브러리 설치와 버전 변경, 되돌리기 어려운 작업, 실행 경로 변경은 그때마다 허락을 받는다.
   - 사용자가 답을 모르면 누구에게 무엇을 물어야 하는지 알려 주고, 외부 확인으로 표시한 뒤 다음 순서로 넘어간다.
   - 권한 표, 보관 기간, 공개 범위, 외부 AI 승인처럼 사용자나 담당자가 정할 내용을 에이전트가 추측해 채우지 않는다.
5. 순서를 하나 마칠 때마다 테스트 결과와 커밋을 확인하고, 점수 변화와 남은 순서를 알린다(예: `78점 → 80점, +2점. 다음은 3번 질문입니다`). 받지 못한 대답은 `README.md`의 "표준 적용 현황"에 적어 새 대화에서 이어 간다.
6. 예상 총점이 80점 이상이면 다시 검사해 새 리포트를 만든다. 예상 점수만으로 80점을 넘겼다고 말하지 않는다. 80점에 못 미치면 2번으로 돌아가 남은 순서를 다시 알린다.
7. 80점을 넘기면 아래 문장으로 알린다. 첫 리포트가 이미 80점 이상이면 2~6번을 건너뛰고 이 문장으로 알린다.

   > NN점으로 1차 목표인 80점을 넘겼지만 이 점수만으로는 통과가 아닙니다. 리포트는 `reports/...-ax-검사-리포트.md`입니다. 필수 항목은 모두 100점이어야 하며, 아직 미달인 필수 항목은 공통 N·N번입니다(없으면 없음). 핸드오프하려면 권장 점수도 90점 이상이어야 합니다. 남은 대답과 확인은 아래와 같습니다. 이어서 진행할까요?

- 대답이나 외부 확인을 받지 못해 80점 전에 더 진행할 수 없으면 현재 점수, 남은 질문, 물어볼 담당자를 알리고 답을 기다린다. 이 경우 완료라고 말하지 않는다.
- 80점을 넘기려고 세부 기준을 줄이거나 지키지 않은 기준을 지킴으로 적지 않는다("채점 방법").

### 리팩토링

사용자가 시작하자고 하면 아래 순서로 한다.

1. 커밋하지 않은 변경이 있으면 사용자에게 알리고 먼저 커밋해 되돌아갈 지점을 만든다(8번). git이 없으면 먼저 설정한다.
2. `ax-refactor/YYYYMMDD-HHmmss` 브랜치를 만들어 그 브랜치에서만 작업한다. main 등 기본 브랜치에서 직접 고치지 않는다.
3. 리포트의 미달 세부 기준을 "규격화와 리팩토링" 순서대로 고친다. 테스트가 없으면 "테스트가 없는 프로젝트"부터 한다.
4. 리팩토링 전에 만든 테스트를 다시 실행해 전후 결과를 비교하고, 이상이 있으면 다음으로 넘어가기 전에 고친다.
5. 다시 검사해 새 리포트를 만들고, 이전 리포트와 비교해 알린다(예: `62점 → 81점, +19점`). 항목별 변화도 리포트에 적는다.
6. 핸드오프 기준을 채우지 못했으면 3번으로 돌아가 채울 때까지 반복한다. 마이그레이션 요청으로 시작했으면 80점을 넘긴 뒤 이어서 진행할지 먼저 묻는다.
7. 핸드오프 기준을 채우면 핵심 흐름을 사용자가 직접 눌러 확인하게 하고, 결과를 리포트의 "동작 검증"에 적는다.

- 시작 동의는 다른 확인을 대신하지 않는다. 큰 변경의 계획 확인("규격화와 리팩토링"), 의존성 업그레이드(5번), 되돌리기 어려운 작업(7번)은 따로 확인을 받는다.
- 사용자 확인이나 외부 조치가 있어야 고칠 수 있는 기준(키 재발급, 승인된 외부 AI 확인 등)이 남으면, 무엇이 왜 막혔는지 사용자에게 알리고 답을 기다린다. 이 기준이 필수 항목에 있으면 해결되기 전에는 핸드오프할 수 없다.
- 기본 브랜치로 합치는 것은 사용자 확인을 받은 뒤에 한다.

### 핸드오프

핸드오프 기준을 채우고 동작 검증까지 마치면 아래 문장으로 안내한다. 기준을 채우지 못했으면 이 문장을 쓰지 않는다. 메일은 사용자가 직접 보내고, 에이전트가 보내지 않는다.

> 필수 항목을 모두 100점으로 채웠고 권장 점수는 NN점입니다. AXTF에 핸드오프할 준비가 되었습니다. 리포트(`reports/...-ax-검사-리포트.md`)는 axtf-support@daewoong.co.kr로 전달해주세요!

## 개발 순서: 스펙 → 행동 → 테스트 → 코드

기능 추가와 버그 수정은 SDD(Spec-Driven), BDD(Behavior-Driven), TDD(Test-Driven) 순서로 한다. 테스트 코드는 선택이 아니다. 테스트를 만들고 실행하지 않은 기능은 완료가 아니다.

| 단계   | 목표                                         | 답할 질문                                          | 산출물                                                                             |
| ------ | -------------------------------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 1. SDD | 무엇을 만들지 코드보다 먼저 글로 합의한다    | 누구를 위해 무엇을 만들고, 어떤 조건이면 완료인가? | `docs/specs/<기능>.md`의 목적·권한·입출력·규칙·수용 기준(AC)                       |
| 2. BDD | 수용 기준을 사용자가 보는 행동 예시로 바꾼다 | 사용자가 무엇을 하면 어떤 결과가 보여야 하는가?    | 같은 파일의 시나리오(S, 전제-행동-결과)와 그 시나리오를 그대로 옮긴 E2E·API 테스트 |
| 3. TDD | 코드 단위가 맞게 동작함을 보장한다           | 이 함수가 이 입력에 무엇을 돌려줘야 하는가?        | 실패하는 단위 테스트 → 통과하는 최소 코드 → 리팩토링                               |

스펙 파일은 아래 형식으로 쓴다.

```txt
# <기능 이름>
## 목적
## 사용자와 권한        # 10번 권한 표 기준
## 입력과 출력
## 규칙
## 수용 기준
- AC-01: ...
## 시나리오
### S-01 (AC-01) <제목>
- 전제: ...
- 행동: ...
- 결과: ...
```

- SDD: 사용자의 요청을 받아 스펙 초안을 에이전트가 쓴다. 수용 기준과 시나리오만 쉬운 말로 사용자에게 확인받는다. 사용자는 화면에서 무엇이 보여야 하는지만 답하면 된다.
- BDD: 수용 기준마다 시나리오를 하나 이상 만든다. 정상 흐름과 함께 잘못된 입력, 권한 없음(15번), 데이터 없음 시나리오를 넣는다. 테스트 이름에 시나리오 ID(S-01)를 넣어 스펙과 테스트를 연결한다.
- TDD: 테스트를 먼저 쓰고 실행해 실패하는 것을 확인한 뒤 코드를 쓴다. 통과하면 리팩토링하고 다시 실행한다. 처음부터 통과하는 테스트는 아무것도 검증하지 않을 수 있으므로 테스트를 다시 본다.
- 버그 수정은 버그를 재현하는 테스트를 먼저 만들어 실패를 확인한 뒤 고친다. 스펙에 빠진 규칙이면 스펙에도 추가한다.
- 테스트를 통과시키려고 테스트를 지우거나, 건너뛰게 하거나(`skip`, `xfail`, `@Disabled`, `.only`), 기대값을 바꾸지 않는다. 기대값을 바꿔야 하면 스펙을 고치고 사용자 확인을 받는다.
- 동작을 바꾸지 않는 리팩토링은 새 스펙 없이 기존 테스트로 확인한다. 테스트가 없는 프로젝트는 아래 "테스트가 없는 프로젝트"를 먼저 따른다.
- 테스트 도구와 위치는 TS-7, PY-6, JV-6을 따른다.

## 규격화와 리팩토링

목표: 같은 스택의 앱은 같은 도구·폴더 구조·아키텍처·코드 스타일을 갖는다. 그래야 다른 사람이나 다른 에이전트가 넘겨받아도 바로 고칠 수 있다.

- 기존 코드를 처음 열면 "AX 검사와 핸드오프"에 따라 검사하고, 리포트의 미달 세부 기준을 `README.md`의 "표준 적용 현황"에 목록으로 남긴다. 고칠 때마다 목록을 갱신하고, 새 대화에서는 이 목록부터 읽는다.
- 고치는 순서:
  1. 현재 동작을 확인하는 테스트를 먼저 만든다. 테스트가 없으면 아래 "테스트가 없는 프로젝트" 순서를 따른다.
  2. 보안 규칙(1~17번) 위반을 고친다.
  3. 버전 고정과 도구(lint·포맷·타입 검사·테스트 명령)를 스택 규칙대로 맞춘다.
  4. 아키텍처(계층 분리, 프론트엔드·백엔드 분리)를 맞춘다.
  5. 폴더 구조와 코드 스타일을 맞춘다. 포맷은 도구로 자동 적용한다.
- 리팩토링은 동작을 바꾸지 않는다. 기능 변경과 리팩토링을 한 커밋에 섞지 않는다.
- 리팩토링 커밋은 `refactor` 타입을 쓰고, 기능 변경과 버그 수정은 `feat`, `fix`로 나눠 커밋한다(8번).
- 한 번에 한 단계씩 고치고, 단계마다 lint·테스트를 실행해 통과하면 커밋한다. 실패하면 그 단계를 되돌리거나 고친 뒤 다음으로 넘어간다.
- 사용자가 다른 기능을 요청한 대화에서는 그 작업이 건드리는 파일만 표준에 맞춘다. 전체 리팩토링은 따로 제안한다.
- 스택 전환, DB 전환, 프론트엔드·백엔드 분리처럼 큰 변경은 계획을 쉬운 말로 설명하고 확인을 받은 뒤 시작한다. 이런 변경은 Strangler Fig 방식으로 한다: 새 구조를 옆에 만들고 기능을 하나씩 옮겨 연결을 바꾼 뒤, 옮긴 기능의 예전 코드를 지운다. 한 번에 전부 다시 쓰지 않는다.
- 리팩토링 기법과 아키텍처 패턴 이름은 마틴 파울러의 『리팩터링』 2판과 『엔터프라이즈 애플리케이션 아키텍처 패턴』(PoEAA)을 따른다. 이 파일에 이름이 나오면 그 정의대로 적용한다.
- 한 단계에는 기법 하나만 적용한다(예: 함수 추출하기 → 테스트 → 커밋 → 함수 옮기기 → 테스트 → 커밋).
- 기능을 넣기 어려운 구조면 먼저 구조를 고쳐 커밋한 뒤 기능을 넣는다.
- 같은 코드가 세 번째 나오면 공통 함수로 뽑는다. 아직 쓰지 않는 확장 지점(추상 클래스, 설정 옵션, 플러그인 구조)은 미리 만들지 않는다.

## SQLite를 PostgreSQL로 옮기기

13번에 따라 SQLite는 쓰지 않는다. SQLite를 쓰는 앱은 사용자가 따로 요청하지 않아도 에이전트가 아래 순서로 PostgreSQL로 옮긴다. 사용자는 개발자가 아닐 수 있으므로 명령과 설정은 에이전트가 실행하고, 사용자에게는 결과와 확인이 필요한 것만 쉬운 말로 알린다. DB 전환은 "규격화와 리팩토링"의 큰 변경이므로 한 단계씩 하고 단계마다 테스트를 실행한 뒤 커밋한다.

1. 찾기: SQLite를 쓴 흔적을 찾는다. SQLite 드라이버·패키지(`sqlite3`, `better-sqlite3`, `sqlite-jdbc` 등), `.db`·`.sqlite` 파일, `sqlite:` 연결 문자열, ORM의 SQLite 방언 설정이 대상이다. 찾으면 어디에 쓰이는지와 데이터가 들어 있는지를 쉬운 말로 알린다.
2. 계획 설명과 확인: 무엇이 바뀌는지(DB 종류, 연결 설정, 필요하면 데이터 이동)와 사용자가 할 일을 설명하고 확인을 받은 뒤 시작한다. 확인 없이 데이터를 지우거나 덮어쓰지 않는다(7번).
3. 로컬 PostgreSQL 준비: 먼저 Docker를 쓸 수 있는지 확인한다(`docker --version`). 사용자 PC에서 가장 쉬운 방법 하나를 골라 안내하고 실행한다.
   - Docker가 있으면 `docker run` 명령 한 줄로 PostgreSQL을 띄운다.
   - Docker가 없거나 쓸 수 없으면 PC에 직접 설치한다. macOS는 Postgres.app이나 Homebrew(`brew install postgresql`), Windows는 PostgreSQL 공식 설치 프로그램을 쓴다. 설치·실행 명령은 에이전트가 안내하거나 실행하고, 관리자 권한이 필요한 설치는 실행하기 전에 사용자에게 먼저 묻는다.
   - 어느 방법이든 연결은 환경 변수 `DATABASE_URL`로 읽고 코드에 직접 쓰지 않는다. `.env`에 값을 넣고 `.env.example`에는 값을 비운 항목을 적는다(1번).
4. 스키마 옮기기: ORM 방언과 드라이버를 PostgreSQL용으로 바꾸고, 마이그레이션 도구가 있으면 그 도구로 PostgreSQL용 마이그레이션을 새로 만든다(도구는 PY-3, JV-3). SQLite와 달라서 깨지기 쉬운 것을 점검한다: 날짜·시간 타입, 불리언, 자동 증가 ID, 대소문자 구분 비교, SQLite 전용 문법.
5. 데이터 옮기기: 기존 `.db`에 남길 데이터가 있으면 PostgreSQL로 옮기고, 테이블별 건수를 옮기기 전과 비교해 사용자에게 알린다. 원본 `.db` 파일은 지우지 않고 보관·삭제를 사용자에게 맡긴다. `.db` 파일은 커밋하지 않는다(3번).
6. 확인: 앱 실행과 테스트를 PostgreSQL로 돌려 통과를 확인한다. 통과하면 SQLite 의존성, 설정, 안 쓰는 코드를 지우고 `README.md`에 DB 실행 방법과 `DATABASE_URL` 항목을 적는다.

## 테스트가 없는 프로젝트

바이브코딩으로 만든 앱은 테스트가 없는 경우가 많다. 테스트 없이 구조를 바꾸면 무엇이 깨졌는지 알 수 없으므로, 리팩토링 전에 아래 순서로 안전망을 만든다.

1. 테스트 도구와 실행 명령을 준비한다(TS-1, PY-1, JV-1).
2. 스모크 테스트: 앱이 실행되는지, 모든 화면과 API가 오류 없이 응답하는지 확인한다.
3. 특성 테스트(characterization test): 지금 코드가 내놓는 결과를 그대로 기록해 기대값으로 삼는다. 결과가 맞는지 판단하는 테스트가 아니라, 리팩토링 뒤에도 같은 결과가 나오는지 비교하는 테스트다. 계산·변환·파일 처리 함수와 API 응답부터 만든다.
4. 핵심 흐름 테스트: 사용자에게 "이 앱으로 가장 자주 하는 일 3가지"를 화면 기준으로 묻고(어느 화면에서 무엇을 누르면 무엇이 나오는지), 그 흐름을 E2E 테스트로 만든다.
5. 권한 테스트(15번).

- 1~4단계를 마치기 전에는 구조를 바꾸는 리팩토링(규격화 4~5단계)을 시작하지 않는다. 포맷 자동 적용, 코드에 적힌 비밀정보 제거(1번)처럼 동작을 바꾸지 않거나 급한 수정은 먼저 해도 된다.
- 테스트 데이터는 실제 자료가 아닌 가짜 데이터로 만든다(3번). 외부 API·AI 호출은 가짜 응답(mock)으로 바꿔 테스트 중에 요금이 나가거나 데이터가 전송되지 않게 한다(2번).
- 특성 테스트를 만들다 버그로 보이는 결과를 발견하면 그 자리에서 고치지 않는다. "표준 적용 현황"에 기록하고 사용자에게 알린 뒤, 리팩토링과 별도 커밋으로 고친다.
- 테스트를 만들 수 없는 부분(테스트용 외부 시스템이 없는 경우 등)은 "표준 적용 현황"에 "테스트 없음"으로 표시하고, 그 부분의 구조 변경은 최소로 한다.
- 이후 새 기능과 버그 수정은 "개발 순서"를 따른다.

## 코드 악취와 대응 기법

아래 신호를 발견하면 오른쪽 기법으로 고친다. 파일·컴포넌트 길이 기준은 스택 규칙(TS-3, PY-2)을 따른다. 언어별 적용 방법은 TS-8, PY-7, JV-7을 따른다.

| ----------------------- | ------------------------------------------------------------- | ---------------------------------------------------------- |
| 기이한 이름             | 이름만으로 하는 일을 알 수 없음(`data`, `temp`, `handle2` 등) | 함수 선언 바꾸기, 변수 이름 바꾸기                         |
| 중복 코드               | 같은 로직이 두 곳 이상                                        | 함수 추출하기, 문장 슬라이드하기, 메서드 올리기            |
| 긴 함수                 | 40줄 초과, 또는 주석으로 구역을 나눈 함수                     | 함수 추출하기, 조건문 분해하기, 단계 쪼개기                |
| 긴 매개변수 목록        | 매개변수 4개 이상                                             | 매개변수 객체 만들기, 객체 통째로 넘기기                   |

## 작업을 마칠 때

- 해당 스택의 lint·포맷·타입 검사·테스트 명령(TS-1, PY-1, JV-1)을 실행하고 오류를 모두 해결한다. 실패하면 완료라고 말하지 않는다. 테스트 결과(통과·실패·건너뜀 개수)와 이번에 추가한 시나리오 ID를 함께 알린다.
- 이번 변경이 공통 규칙과 해당 스택 규칙에 어긋나지 않는지 스스로 점검하고, 결과를 쉬운 말로 짧게 알린다. 리팩토링을 했으면 "표준 적용 현황"을 갱신한다.
- 사용자가 "규칙 파일 기준으로 점검해줘"라고 하면 공통 1~17번과 해당 스택 규칙을 하나씩 확인해 점수를 매기고 리포트를 만든다("AX 검사와 핸드오프").
- 코드를 수정한 뒤에는 앱이 예전처럼 동작하는지 사용자가 직접 눌러 확인하도록 안내한다. 사용자가 해결하기 어려워하면 소속 부서의 현업 배치 개발자에게 도움을 요청하도록 안내한다.
